## `security-1` — A threat model that is a test: three deployment profiles, a control matrix, and a test that keeps the matrix honest

**survived 3/3, with corrections · effort M · impact 4/5**

**What the code does today.** There is no threat model; the trust assumptions live as inline comments. server.py:96-99: "Trusting any peer is safe here because the container is only reachable through that proxy" — an assumption about a deployment profile that no document names. SECURITY.md:12-21 scopes what is *in* scope but never says who the adversary is. formatter.py:20-34 (_oneline) and formatter.py:113-124 (format_error) each argue one control in isolation. The audit's finding 11 (audit.md:230-235) lists the hosted-endpoint gaps as "things to settle before a hosted endpoint exists" but attaches them to no profile. Telemetry puts every search term on a span — dataset.py:320 `db.query.text` and search_operations.py:85 `df.keyword` — and docs/development/observability.md:77-78 documents that without classifying it as personal data when joined to a client address. The project already pins prose to code (test_search_invariants.py:80-85 asserts the fuzzy docstring against DEFAULT_FUZZINESS); nothing pins a security claim to the test or workflow step that enforces it.

**The gap.** Controls cannot be classified as sound, missing or performative because there is no statement of what they defend, against whom, in which deployment. Concretely, the same code is (P1) a stdio child of a desktop MCP host on a laptop, (P2) a container behind a TLS proxy (docker-compose.yml, the documented shape), and (P3) a future internet-facing endpoint; the controls that matter differ per profile and today's comments assume P2 everywhere.

**The proposal.** Write docs/development/threat-model.md with this outline, then make it executable. PROFILES. P1 stdio-on-laptop: boundary = MCP host process <-> stdin/stdout; adversaries = hostile corpus text reaching the model, a hostile or corrupt mounted table (lance files parsed by Rust in-process), unprefixed env (`PORT`, `HOST`, settings.py:23-24); assets = the user's model context and citation integrity; egress = only OTLP when KA_MCP_OTEL_ENABLED. P2 behind-proxy: boundary = proxy <-> container; adversaries = whoever the proxy admits, co-tenants; assets add host CPU/RAM (10k rows x worker threads, dataset.py:326), dataset paths (format_error), search terms on spans. P3 hosted: boundary = internet <-> listener; adversaries add unauthenticated clients, browser-originated DNS-rebinding (host_origin_protection defaults False in FastMCP 3.4.4), X-Forwarded-* spoofing (forwarded_allow_ips="*"), session-table exhaustion (stateful streamable HTTP by default), compute abuse; assets add the operator's bill and user privacy. SUPPLY CHAIN (all profiles): assets = the release identity (cosign/SLSA), `main` (no branch protection), the docs Pages identity (docs.yml has pages:write + id-token:write), Dependabot auto-merge with contents:write. CONTROL MATRIX. One row per control: control | profile(s) | status in {enforced, documented-only, performative} | enforced-by (test function or workflow step). Classify today: enforced = SQL predicate escaping (test_dataset), error-type-only disclosure (test_formatter), USER 1000, digest pins, 686/686 hashed lock entries; performative = cosign signature (no verify recipe with identity constraints; nothing verifies it in CI), SLSA badge before any tag exists (README:214-216 admits this), test-published (health only, serve.go TestPublished), "Trivy scans the published image" (SECURITY.md:27 — it scans a rebuild); missing for P3 = auth, host/origin validation, trusted-proxy list, cost bounds, rate limit, stateless sessions. EXECUTABLE. packages/kansallisarkisto-mcp/tests/test_threat_model.py parses the matrix table from the markdown, and for every row marked `enforced` asserts the named pytest node id exists (collect via `pytest --collect-only -q` or import + getattr) or the named workflow step name appears in .github/workflows/*.yml. A row that cites a test that was deleted fails CI; a control cannot silently become performative. Add a `profile` column to docs/development/deployment.md so an operator picks a profile, not a list of settings.

**Why it is once-in-a-lifetime.** The project's distinguishing habit is prose that is load-bearing and checked by tests. Extending that to the security claims — every control names its enforcement point and a test refuses to let the claim outlive the enforcement — is something no archival MCP server has, and it is the artefact a Kansallisarkisto or Riksarkivet security review would actually read.

**How we would know.** threat-model.md exists with >= 20 matrix rows; test_threat_model.py passes and fails when any cited test or workflow step is renamed (demonstrate by renaming one in a scratch branch); zero rows in state `performative` at the time of the first tagged release, or each one carries a linked issue.

**Risks.** A matrix nobody updates rots like any doc — the test only guards the enforcement side, not new controls. Classifying the cosign signature as performative will read as harsh; it is accurate until a verify recipe exists. Argues mildly against the project's inline-comment style by moving the trust assumptions to one page — keep the inline comments and have them cite the profile.

**First step.** One PR: threat-model.md with the three profiles and a 12-row matrix covering the controls already in code, plus test_threat_model.py asserting those 12 rows' test node ids resolve. No behaviour change.

**Spike.** From the repo root: `/tmp/uvenv/bin/uv run pytest --collect-only -q packages | grep -c '::'` to get the node-id inventory; write a 12-row markdown table into the scratchpad citing e.g. `packages/kansallisarkisto-mcp/tests/test_formatter.py::test_a_newline_in_a_field_cannot_forge_a_result_record`; a 20-line script parses the table and checks each id is in the inventory. This proves the parse-and-assert mechanism in under an hour with no network.

## `security-2` — A hosted-endpoint profile in settings: token/JWT auth, host-origin protection, trusted proxies, stateless sessions and a per-client rate limit — every one a no-op on stdio

**survived 3/3, with corrections · effort L · impact 5/5**

**What the code does today.** server.py:100-105 runs HTTP with `uvicorn_config={"proxy_headers": True, "forwarded_allow_ips": "*"}` and nothing else; tools.py:17-69 constructs FastMCP with no `auth` and no `middleware`. settings.py:21-25 has exactly five fields (ka_lancedb_uri, ka_mcp_transport, host, port, log_level). Verified against the installed fastmcp 3.4.4: `FastMCP.__init__` takes `auth` and `middleware`; `run_http_async` takes `stateless_http`, `host_origin_protection` (default False), `allowed_hosts`, `allowed_origins`, `middleware`; `fastmcp.server.auth.providers.jwt` exposes `StaticTokenVerifier(tokens, required_scopes)` and `JWTVerifier(public_key|jwks_uri, issuer, audience, required_scopes, ssrf_safe)`; `fastmcp.server.middleware.rate_limiting.RateLimitingMiddleware(max_requests_per_second, burst_capacity, get_client_id, global_limit)` exists. Streamable HTTP is stateful by default (`stateless_http=False`), so every unauthenticated client allocates a session. df_tool.py:1-11 explains tools are sync and run in a worker threadpool — so concurrency is bounded only by anyio's default thread limiter, and each worker can hold a 10k-row materialisation (dataset.py:326).

**The gap.** For P3 (hosted) the server has no way to say who may call it, which Host it answers to, which proxies it believes, or how much one client may spend. All of it is one env-gated block away, and the project's philosophy ("stdio on a laptop must cost nothing") is satisfiable because every control here is constructed only when its setting is set.

**The proposal.** settings.py gains, all prefixed KA_MCP_ and all defaulting to off: `auth: Literal["none","static","jwt"] = "none"`; `auth_tokens: SecretStr` (static: comma-separated `token:scope` pairs; document that it is for a single-tenant proxy setup, not multi-user); `auth_jwks_uri`, `auth_issuer`, `auth_audience` (jwt); `allowed_hosts: list[str]` (when set: `host_origin_protection="strict"`, `allowed_hosts=...`, `allowed_origins=[]`); `trusted_proxies: str = "127.0.0.1"` replacing the literal "*" — compose keeps working by setting it to the proxy network CIDR, and the server.py:96-99 comment becomes the docstring of the setting; `stateless: bool = True` for http (the tools are pure functions; there is no session state to keep, and stateless removes the per-client session table and makes horizontal scaling trivial); `rate_limit_rps: float = 0` (0 = off) -> `RateLimitingMiddleware(max_requests_per_second, burst_capacity=5*rps, get_client_id=<token subject if authenticated else request.client.host after proxy resolution>)`; `max_inflight_searches: int = 0` -> a `threading.BoundedSemaphore` acquired in `lancedb_fts_search` around `to_list()` (dataset.py:326) with a 2 s acquire timeout that raises `SearchInputError("the server is busy; retry in a moment")` — text the model can act on, per the tools-never-raise rule. Build the auth provider in a new `security.py` `build_auth(settings) -> AuthProvider | None` and pass it to FastMCP in tools.py:17; build middleware in `server.main()` only under the http branch. stdio path constructs nothing (assert in test_server.py that `kansallisarkisto_mcp.middleware == []` and `auth is None` when transport is stdio). Tests: boot the ASGI app via `kansallisarkisto_mcp.http_app()` with httpx: 401 without bearer, 200 with; Host header outside allowed_hosts -> 421/403; 20 rapid calls at rps=5 -> RateLimitError surfaced as a tool error the model can read; 8 concurrent searches at max_inflight=2 -> some return the busy text, none raise. Docs: deployment.md gets a "Hosted endpoint" section listing the six variables and the compose diff.

**Why it is once-in-a-lifetime.** Most public MCP servers either ship no auth or hardcode a vendor's OAuth. This makes the authentication story a *profile switch* that is provably zero-cost in the laptop profile, using the server framework's own verified primitives rather than a bespoke middleware — and pairs it with the compute bound (semaphore) that the 10k-materialisation design uniquely needs. It is the reference answer to "how do I host an archival MCP server for a class of 40 students without a bill shock".

**How we would know.** With KA_MCP_AUTH=static and no token, `curl -X POST /mcp` returns 401 and the smoke client fails; with a token, scripts/mcp_smoke.py passes all 6 checks unchanged. With max_inflight_searches=4 and 64 concurrent worst-case searches (`keyword="och", match_all=false, limit=100`) on the full df table, peak RSS stays under 2x the idle RSS (measure with /usr/bin/time -v) versus the unbounded run. `pytest -q` wall time and the stdio boot time are unchanged (+/-5%).

**Risks.** Stateless mode changes the transport handshake (no Mcp-Session-Id); the fastmcp Client in mcp_smoke.py handles it, but an old client might not — make it a setting, default on only when auth is on if that proves too sharp. Static tokens are a single-tenant tool; the docs must say so or someone will ship them to 40 students. `forwarded_allow_ips` default change from "*" to loopback is a behaviour change for anyone running the container behind a proxy on a different network — call it out in the changelog and in compose. A rate limit keyed on client IP behind a misconfigured proxy limits the proxy, not the client — which is exactly why trusted_proxies must be set first.

**First step.** PR 1 (S): `trusted_proxies` and `allowed_hosts` settings replacing the literal "*" in server.py:104, with the compose file updated and two tests. PR 2: auth. PR 3: rate limit + semaphore.

**Spike.** Runnable here with no network: `uv run python -c` that builds `FastMCP(auth=StaticTokenVerifier({"t":{"client_id":"x","scopes":[]}}))` around the existing tools, calls `mcp.http_app(stateless_http=True, host_origin_protection="strict", allowed_hosts=["localhost"])`, and drives it with `httpx.ASGITransport` to show 401 -> 200 and a Host-header rejection; then time 200 sequential `/mcp` initialize+call round-trips with and without auth to bound the overhead (expect < 1 ms per call).

## `security-6` — Dependency cooldown and a hash-locked docs build: sit out the malicious-release window and stop floating packages from holding a Pages deploy identity

**survived 3/3, with corrections · effort S · impact 3/5**

**What the code does today.** .github/dependabot.yml has no `cooldown` block for any of its four ecosystems (grep confirms none), and pyproject.toml has no `[tool.uv] exclude-newer`. dependabot-auto-merge.yml:29-31 merges green patch/minor bumps with `contents: write` and `main` has no branch protection (audit 11, dependabot-auto-merge.yml:9-11), so a freshly published patch release of any of the 100 locked packages (uv.lock: 100 packages, 686 hashed artefacts) can land on `main` the Monday after it appears, gated by tests and pip-audit — which cannot know about a compromise that has no advisory yet. docs.yml:26 `pip install zensical==0.0.60` pins the top-level version only; its transitive dependencies resolve fresh at each run inside a job with `pages: write` and `id-token: write` (docs.yml:10-13), i.e. a compromised transitive release could publish arbitrary content to ai-riksarkivet.github.io/kansallisarkisto-mcp. publish.yml:137-139 installs an unversioned git-cliff (covered in security-5).

**The gap.** Both auto-merge and the docs build accept the newest artefact on the day. Most malicious PyPI/npm releases are detected and yanked within days; a short cooldown removes most of that exposure at zero engineering cost, and the docs job should install exactly what was reviewed.

**The proposal.** dependabot.yml: add to each ecosystem `cooldown: {default-days: 7, semver-major-days: 30, semver-minor-days: 7, semver-patch-days: 7}` (pip, gomod, docker, github-actions). pyproject.toml: `[tool.uv] exclude-newer = "<lock date minus 7 days>"`, bumped whenever `uv lock` is run (add `make lock` that sets it from `date -d '7 days ago'`), so a local `uv lock` can never resolve to something younger than a week either. docs.yml: replace the pip install with `uv sync --only-group docs --frozen` after adding a `docs = ["zensical==0.0.60"]` dependency group to the root pyproject.toml so the docs stack is in uv.lock with hashes and covered by Dependabot, pip-audit and the cooldown; or, if keeping pip, `uv pip compile --generate-hashes docs/requirements.in -o docs/requirements.txt` and `pip install --require-hashes -r docs/requirements.txt`. Record the policy in SECURITY.md next to the auto-merge sentence (SECURITY.md:34): "patch and minor bumps merge automatically once tests pass and the release is at least 7 days old".

**Why it is once-in-a-lifetime.** Not glamorous, but it is the single cheapest change that alters the project's exposure to the supply-chain incident class that actually happens (a hijacked maintainer account pushing a patch release), and it makes the auto-merge policy defensible in a threat model rather than merely convenient.

**How we would know.** `dependabot.yml` validates in the GitHub UI with cooldown shown; the next Monday's PRs contain no package version younger than 7 days (check the PR body's release dates); `uv lock --check` passes with `exclude-newer` set; docs.yml installs from the lockfile and fails if the hash of any docs dependency changes without a lockfile change.

**Risks.** A 7-day cooldown delays security fixes by 7 days too — Dependabot security-alert PRs are exempt from cooldown by design, so keep `open-pull-requests-limit` for those. `exclude-newer` makes `uv lock` deterministic in time, which surprises anyone expecting the newest version; the Makefile target documents it. zensical is pre-1.0 and moves fast; putting it in uv.lock means its updates go through the same grouped-PR path the audit's finding 5 says rarely auto-merges — acceptable for docs.

**First step.** One PR: the cooldown block in dependabot.yml, `exclude-newer` in pyproject.toml with a `make lock` target, and the docs dependency group. Under an hour.

**Spike.** Offline: `uv lock --exclude-newer 2026-09-01T00:00:00Z --check` in a scratch copy of the repo to confirm the current lock already satisfies a 7-day exclusion (it should — uv.lock is committed); if it does not, the diff names exactly which packages are younger than a week, which is the exposure being measured.

## `security-8` — A signed data manifest: make the mounted table — the half of the deployment the image does not contain — provenanced, citable and verifiable like the image

**survived 3/3, with corrections · effort M · impact 4/5**

**What the code does today.** The image ships no data (Dockerfile:67-70); the table is built by `scripts/harvest.py` from `https://sisaltohaku.demo.kansallisarkisto.fi` (harvest.py BASE_URL; a *demo* host) via `urllib` with no integrity signal beyond TLS, appended slice by slice into `df.jsonl.gz`, then `ingest_df` (ingest.py:106-152) builds the table and indexes. Nothing records what was harvested when, from which URL, with which checksum, by which code version or with which index configuration; `report.json` (harvest.py, harvest_index) records coverage but not a hash. server.py:49 logs only table names at boot; `/ready` returns `{"status":"ready","table":"df"}` (routes.py:55). The tool text tells the model to "cite the archive, not this snapshot" (README:204-206) but gives no snapshot identity to cite. Everything the model reads comes from that table, and the only invariant checked on it is `--verify`'s unique objectIDs (harvest.py verify()). The audit's own numbers drift between snapshots already (27 vs 28 compound-language charters, audit.md:187-188).

**The gap.** The corpus is the attack surface and the trust anchor at once, and it is the one artefact with no provenance: an operator cannot tell which harvest a server is serving, a historian cannot cite the snapshot a quotation came from, and an altered table (upstream edit, MITM on a demo host, a tampered mount) is indistinguishable from a legitimate re-harvest.

**The proposal.** (1) harvest.py writes `<index>/<index>.sha256` and adds `source_url`, `harvested_at`, `sha256`, `harvest_script_version` (git describe) to report.json. (2) ingest.py `ingest_df` writes `<lancedb_uri>/df.manifest.json`: `{table, source: {url, harvested_at, jsonl_sha256, coverage_pct}, records: {kept, skipped}, census: {newline_fields, cf_chars, cc_chars, untranscribed}, index: {language, stem, remove_stop_words, with_position, ascii_folding, max_token_length}, lib_version, ingested_at}` — the same facts test_search_invariants.py:46-58 asserts, recorded at build time. (3) server.py `log_table_status` reads and logs the manifest at boot beside the table list; `readiness()` returns `snapshot: {harvested_at, records}` in `/ready` (routes.py:51-56); `format_results` (dataset.py:446-479) adds one header word: "… showing 25 of 1,451 records (offset 0; snapshot 2026-07-12)" so the model can pass the snapshot date to the historian, satisfying README:204's request concretely. (4) Verifiability: `make ingest-df` optionally runs `cosign sign-blob --bundle df.manifest.sigstore.json df.manifest.json` with the same keyless flow the image uses; `scripts/verify_data.py` checks the bundle identity and recomputes the jsonl sha256 — an operator mounting a table someone else built can verify who built it and from what. (5) The manifest's index block replaces the fixture-only assertion as the *served* configuration: `/ready` can refuse (503, reason "index config differs from manifest") if the on-disk FTS index config disagrees with the manifest, catching a table built by an older lib.

**Why it is once-in-a-lifetime.** Every other control in this repository protects code; the model reads data. A signed, citable data manifest extends SLSA-style provenance from the image to the corpus it serves, gives the historian the snapshot identity the README asks them to cite, and makes "the index was built the way the reasoning assumes" a property of the deployment rather than of the test fixture. No archival MCP server does this; it is the piece an archive's own security or records-management review would ask for first.

**How we would know.** `make ingest-df` produces df.manifest.json; boot log and `/ready` show the snapshot; every `df_search` header carries the snapshot date; `scripts/verify_data.py` exits 0 on a freshly built table and non-zero after one byte of df.jsonl.gz is changed or the manifest is edited; the manifest census numbers for the df corpus are recorded in data-sources.md replacing the asserted "no record contains one".

**Risks.** The manifest is written next to the table, so the `data:/data:ro` mount and the uid-1000 ownership rules (deployment.md) apply — write it in the ingest step, never at serve time. Signing needs an OIDC identity at ingest time (a developer's GitHub login via `cosign sign-blob` interactive flow, or a CI job); make it optional and verified-if-present. Adding a date to every search header changes tool output for every consumer and every formatter test; keep it to the header line. The upstream demo service offers no checksum, so the manifest attests what *we* fetched, not what the archive published — say so in the docs; the real fix upstream is an authenticated ES endpoint with an API key (harvest.py docstring already notes it exists).

**First step.** One PR: `ingest_df` writes the manifest (source block filled from report.json if present, else nulls), `log_table_status` logs it, `/ready` includes it, one test on the fixture asserting the manifest's index block equals what `list_indices()` reports. Signing and the header date in a second PR.

**Spike.** Runnable here: ingest the fixture into a temp dir, write the manifest with the census (newlines/Cf/Cc per field — measured 0/0/0 on the fixture), read back `table.list_indices()[..].index_details` and diff it against the manifest's index block; then `sha256sum` the fixture file (19,105 bytes) to check the cost model — extrapolate to the 6.3 GB tuomiokirjat export at ~500 MB/s to confirm the hash adds under a minute to a 1.5-hour harvest.
