# Resilience and failure modes

Every proposal from this lens in full, followed by the three skeptics' verdicts on it.
Effort and impact are the lens's own estimates; the verdict tally is the skeptics'.

## `resilience-1` — A real per-call deadline: lance's native query timeout, because FastMCP's timeout= is a silent no-op for these tools

**pending (0/3 verdicts in) · effort M · impact 5/5**

**What the code does today.** dataset.py:326 runs `query.limit(MAX_TOTAL_COUNT).to_list()` with no deadline; df_tool.py:87-218 registers both tools with no `timeout=`. Both handlers are sync and dispatched to anyio's threadpool (df_tool.py module docstring; test_tools.py:107). Measured (scratchpad/spike_timeout.py): a FastMCP tool declared `@mcp.tool(timeout=0.5)` that sleeps 3 s returned `done`, is_error=False, after 3.01 s — the timeout never fired. Cause: fastmcp/tools/function_tool.py:401 wraps the await in `anyio.fail_after`, but anyio's `run_sync_in_worker_thread` (anyio/_backends/_asyncio.py:2671) runs it under `CancelScope(shield=not abandon_on_cancel)` with abandon_on_cancel=False, so the scope is shielded and the deadline is discarded; had it fired it would raise `McpError(-32000)` — a protocol error the project's philosophy forbids. Meanwhile lancedb 0.38's `to_list(timeout=timedelta)` (lancedb/query.py:1132) is a real Rust-side deadline: measured on a 200k-row synthetic table (spike_native_timeout.py), an 8-word fuzzy=2 OR query took 1,154 ms unbounded and with timeout=5/50/200 ms raised `RuntimeError: lance error: Query Execution error: Execution error: Query timeout after N ms` after 229/245/219 ms — i.e. it aborts within ~250 ms of the deadline. Today that RuntimeError would reach the model as `Error: the search failed with an internal RuntimeError` (formatter.py:316), indistinguishable from a broken table. A stdio client that closes the pipe mid-query (spike_stdio_disconnect.py) leaves the server running the query to completion — 5.8 s after stdin closed for a 6 s tool — because anyio worker threads are non-daemon; only a deadline bounds that.

**The gap.** No query can be bounded in time. A model retrying fuzzy=2 on a long keyword against 7.8M tuomiokirjat pages holds a worker thread for as long as lance takes; a wedged S3/NFS read holds it forever; the boot probe (server.py:67) and readiness (tools.py:96-111) can hang the process or the probe on a stalled mount. Adopting FastMCP's own `timeout=` would look like a fix and do nothing.

**The proposal.** In dataset.py add `DEFAULT_QUERY_DEADLINE = timedelta(seconds=10)` (df searches run in ~7 ms; a 32-way hammer on 200k rows had a median of 10 s, so 10 s is a ceiling nobody legitimate hits) and `PROBE_DEADLINE = timedelta(seconds=2)`; give `lancedb_fts_search` a `deadline: timedelta | None = DEFAULT_QUERY_DEADLINE` keyword and pass it as `to_list(timeout=deadline)` (line 326); same for `get_charter`'s `.to_list()` (search_operations.py:193). Add `class SearchBudgetError(SearchInputError)` and, in the `except Exception` at dataset.py:327, re-raise a lance error whose message contains `Query timeout after` as `SearchBudgetError(f"the search exceeded its {deadline.total_seconds():.0f}s budget; narrow it — drop fuzzy, add a language/place/year filter, or use fewer words — and try again")`, so `_answer` (df_tool.py:44) returns that sentence verbatim with `mark_span_error(..., 'budget')`. Expose `KA_QUERY_DEADLINE_SECONDS` in settings.py and thread it through `DfSearch`. `probe_table_readable` (server.py:67) and `readiness()` run with `PROBE_DEADLINE` so a hung mount produces a 503 in 2 s rather than a stuck probe. Record the deadline on the span as `db.query.deadline_ms` and count `kansallisarkisto.lancedb.errors{error.type=budget}` separately from server faults.

**Why it is once-in-a-lifetime.** It converts an unbounded resource into a documented contract the model can act on — 'narrow it' is a real next move for a language model, 'internal RuntimeError' is not — and it is measured rather than assumed: the project would be the first MCP server to document that FastMCP's per-tool timeout is inert for sync tools and why, with the anyio line cited.

**How we would know.** test: a monkeypatched `to_list` that sleeps 3 s with deadline=timedelta(milliseconds=200) returns text starting `Error: the search exceeded its` within 500 ms and never a protocol error; on the 200k synthetic table the fuzzy=2 8-word query with a 1 s deadline aborts in ≤1.3 s (today: 1.15 s unbounded, would be ~40 s at 7.8M rows by linear extrapolation); p99 of `kansallisarkisto.lancedb.query.duration` is provably ≤ deadline + 0.3 s under a 60-call fuzzy=2 hammer; `/ready` answers within 2.5 s when `to_list` is stalled.

**Risks.** lance's timeout granularity is ~220 ms, so sub-second deadlines are approximate; a timed-out query kept the tokio pool busy briefly (a cheap query immediately after took 424 ms vs ~10 ms), so the deadline bounds the caller, not the CPU — pair with resilience-4. The remote (LanceDB Cloud) client path may treat timeout differently; only the local path was measured. Argues against nothing the project states, but a deadline-hit search has no `total_hits`, so the formatter's honest-total promise needs an explicit 'not counted' branch.

**First step.** One PR: `deadline` parameter on `lancedb_fts_search` and `get_charter`, `SearchBudgetError`, the classifier for `Query timeout after`, the `_answer` branch, and two tests (monkeypatched slow `to_list`; real fuzzy query on a 5k-row fixture blown up from df_sample with a 1 ms deadline asserting the sentence).

**Spike.** Already run: scratchpad/spike_timeout.py (FastMCP timeout=0.5 on a 3 s sync tool → 'done' after 3.01 s) and scratchpad/spike_native_timeout.py (lance timeout fires at 229/245/219 ms for 5/50/200 ms deadlines on a 200k-row table built by spike_cost.py). Re-runnable offline with `/tmp/uvenv/bin/uv run --project /home/user/kansallisarkisto-mcp python spike_native_timeout.py`.

## `resilience-2` — Two-phase search: rank 10k row ids, fetch only the page — a bytes budget per call that removes the OOM and the GIL serialisation

**pending (0/3 verdicts in) · effort L · impact 5/5**

**What the code does today.** dataset.py:243-254 documents the pattern: every search materialises up to MAX_TOTAL_COUNT rows of every non-FTS column to count them, then keeps `limit`; it measured 6.1 → 3.3 MB on df by projecting away `searchable_text`. Measured on a 200k-row table with tuomiokirjat-shaped 2.5 KB pages (scratchpad/spike_cost.py, spike_hammer.py): today's `select(all).limit(10000).to_list()` = 256 ms, 22.2 MB of transcript text per call, RSS +260 MB for one call; 8 concurrent calls took 2.0 s wall = exactly 8 × 0.256 s — zero parallel speed-up, because `to_list` → `to_pylist()` (lancedb/query.py:1146) builds 10,000 Python dicts under the GIL; 32 concurrent 8-word OR searches at fuzzy=0 took 12.9 s wall, median per-call 10.1 s, RSS 292 → 2,570 MB. anyio's threadpool admits 40 (anyio/_backends/_asyncio.py:3162 `CapacityLimiter(40)`), so 40 × ~70 MB ≈ 2.8 GB is the reachable peak in a container. Two-phase measured on the same table: `select(['_score']).with_row_id(True).fast_search().limit(10000).to_arrow()` then `table.take_row_ids(page_ids).select(cols).to_list()` = 24 ms total (page fetch 5.6 ms, order preserved), ~160 KB moved instead of 22 MB. lancedb's default `read_consistency_interval=None` (lancedb/db.py:764-768) pins a `LanceTable` handle at the version it opened, and `lancedb_fts_search` opens a fresh handle per call (dataset.py:290), so both phases see one version and row ids stay valid across the two.

**The gap.** The 10k materialisation is the single scaling hazard: per-call bytes and GIL time are proportional to row width, not page size, so tuomiokirjat (2.5 KB pages) is ~10× df's cost per call and 40 concurrent calls can OOM-kill a 2 GB container — which then fails /health and crash-loops under exactly the load that caused it. The project's stated goal 'scales to 7.8M pages without changing shape' is not true of this line.

**The proposal.** Rewrite the execution half of `lancedb_fts_search` (dataset.py:306-343): phase 1 `query.select(['_score']).with_row_id(True).where(where).fast_search().limit(MAX_TOTAL_COUNT).to_arrow(timeout=deadline)` → an Arrow table `ranked`; `total = ranked.num_rows`; `page_ids = ranked.column('_rowid').slice(offset, limit).to_pylist()`; phase 2 `table.take_row_ids(page_ids).select(columns).to_list()` on the same `table` handle, re-attach `_score` from `ranked.column('_score').slice(offset, limit)`. Keep the docstring's argument for one ranked set (BM25 ties) — it still holds, the ranked set is just ids now — and replace the 6.1→3.3 MB paragraph with the new numbers. Add `MAX_PAGE_BYTES = 2 MB` as a formatter-side guard (100 × full transcripts can exceed what a model context should receive) that truncates snippets rather than rows. Record `db.response.bytes` on the span. Pin with a test that phase 1's schema is exactly `{_score, _rowid}` and that a 100-row page never transfers more than `limit` transcripts (monkeypatch `take_row_ids` to count).

**Why it is once-in-a-lifetime.** It makes 'no count API' a solved problem for LanceDB FTS in the open: an honest total plus stable pagination at ~1% of the bytes, measured, with the version-consistency argument written next to it — the pattern every LanceDB-backed archive server will copy.

**How we would know.** On the 200k synthetic table: per-call ≤30 ms (today 256 ms); 32 concurrent searches add <150 MB RSS (today +2.3 GB) and finish in <2 s wall (today 12.9 s); 8 concurrent calls show ≥3× speed-up over serial on 4 CPUs (today 1.0×). On the real df table the 1,451-hit query cited in dataset.py:252 moves <100 KB in phase 1 instead of 3.3 MB.

**Risks.** `take_row_ids` is documented as 'row ids are not stable and are relative to the current version' — safe here only because the handle is pinned per call; a future switch to `read_consistency_interval=0` or a long-lived handle would silently break it, so the test must assert the handle is opened per call. `_rowid` semantics differ on the remote client. The formatter's `_score` attachment is new code on the hot path. This overrides the documented projection reasoning at dataset.py:249-254 — the comment must be rewritten, not left contradicting the code (the second audit's finding 8 shows what stale prose costs here).

**First step.** PR 1: implement phase 1/phase 2 behind a module flag `TWO_PHASE = True`, keep the old path for A/B in a benchmark script under scripts/, and port the invariants tests (test_search_invariants.py:133-175: tiling, order stability, page ≤ limit) unchanged — they are the contract.

**Spike.** Already run: scratchpad/spike_cost.py (builds cost_db: 200k rows in 19 s, 693 MB; A=256 ms/22 MB vs C=24 ms) and scratchpad/spike_hammer.py (32-way: +2.3 GB, median 10.1 s). The take_row_ids page fetch (5.6 ms, order preserved) was confirmed inline. Rerun: `/tmp/uvenv/bin/uv run --project /home/user/kansallisarkisto-mcp python spike_cost.py 200000`.

## `resilience-3` — A failure taxonomy and a degraded-state machine: classify lance errors, tell the model whether to retry, flip /ready, and fast-fail through a circuit breaker

**pending (0/3 verdicts in) · effort L · impact 5/5**

**What the code does today.** df_tool.py:51-56 folds every non-input exception into `format_error`, which returns only the type (formatter.py:316); every lance failure is a `RuntimeError`, so the model always reads `Error: the search failed with an internal RuntimeError`. Measured (scratchpad/spike_corrupt.py) on a real fixture table: FTS index files truncated to 0 bytes → `RuntimeError: lance error: Not found: …/_indices/<uuid>/tokens.lance` — byte-for-byte the same message deployment.md:49 documents for the EACCES/uid-1000 case; `_indices/` deleted → same `Not found`; a data fragment truncated to half → `RuntimeError: lance error: LanceError(IO): Generic LocalFileSystem error: failed to fill whole buffer`; `data/` deleted → `Not found: …/data/<fragment>.lance` while `table_names()` still lists `df`; `_versions/` deleted → `ValueError: Table 'df' was not found` while `table_names()` still lists `df` (so `get_search` at tools.py:88-89 passes and the tool reports an internal ValueError rather than the missing-table sentence); the deadline case (resilience-1) → `Query timeout after N ms`. `readiness()` (tools.py:96-111) reported `(True, 'df')` after `_indices/` was deleted because the facade is cached (the second audit's finding 1 covers the caching; it does not cover that even an uncached probe has no way to say *what kind* of broken). `mark_span_error` (df_tool.py:54) tags these `df_search failed: RuntimeError` — one bucket for permanent corruption, transient I/O and deadlines alike.

**The gap.** Neither the model nor an orchestrator can distinguish 'retry' from 'stop, the archive is down' from 'narrow your query'. A model that gets `internal RuntimeError` on a permanently unreadable table will retry with variations — the hammer case — and every retry re-touches the broken index; /ready stays 200; the error metric has one flat class.

**The proposal.** In dataset.py add `class FailureClass(StrEnum): missing, unreadable, corrupt, budget, transient` and `classify_lance_error(exc) -> FailureClass`: `Table '…' was not found` → missing; `Not found:` with `/_indices/` or `/data/` in the path → unreadable (permanent until an operator acts — the text names the two causes: ownership vs half-copied table); `failed to fill whole buffer`, `Invalid`/`Corrupt` → corrupt; `Query timeout after` → budget; everything else transient. Wrap as `class TableFaultError(RuntimeError)` carrying the class and a caller-safe sentence (never the path). In df_tool.py `_answer` add a branch: missing/unreadable/corrupt → `Error: the Diplomatarium Fennicum table on this server is unreadable (…cause…). Retrying will not help; tell the user the archive search is temporarily unavailable.`; budget → the resilience-1 sentence; transient → `Error: a temporary storage error; retry once.` In tools.py add `_state: dict` = {class, since, count} updated on every fault and cleared on success; `readiness()` returns 503 with `{'status':'not ready','class':'unreadable','since':…}` when the last fault is permanent-class, and re-runs the 2 s probe every 30 s (half-open) so a late mount or a fixed chown recovers without a restart. Circuit breaker: after 3 consecutive permanent-class faults, `_answer` returns the sentence without touching lance until the next half-open probe succeeds (fast-fail, ~0 ms instead of a failing index read). Metrics: `kansallisarkisto.lancedb.errors{error.type=<class>}` and a `kansallisarkisto.lancedb.state` gauge (0 ready/1 degraded/2 down). Document the matrix in observability.md: failure → sentence the model reads → /ready body → metric label.

**Why it is once-in-a-lifetime.** It gives the three consumers of a failure — the model, the orchestrator, the dashboard — one shared vocabulary derived from measured error strings, so 'boots without data, a missing table is a message' extends to 'a broken table is the right message', and a model stops hammering a dead server because it was told to.

**How we would know.** Fault-injection tests (resilience-8) assert for each of the five injected states: the exact tool sentence prefix, `/ready` status code and `class`, and the `error.type` label; the breaker makes the 4th call on an unreadable table return in <1 ms without a lance call (assert via a counting monkeypatch); after restoring the table, `/ready` returns 200 within one half-open interval without a restart; the `df_search failed: RuntimeError` span status string no longer appears anywhere.

**Risks.** Classification is by substring on lance's Rust error text, which is not an API — pin each string with a test that builds the real corruption so a lance upgrade that rewords the message fails loudly rather than silently reclassifying. Fast-fail on 3 consecutive faults could mask a flapping mount; the half-open probe bounds that to 30 s. The breaker is process state, so two replicas can disagree — fine, /ready is per replica. Adds a moving part to a design that prizes having none.

**First step.** PR: `classify_lance_error` + `TableFaultError` in dataset.py with five substring tests built from real corrupted fixture tables (each takes ms — spike_corrupt.py shows the recipes), and the `_answer` branch that returns the class-specific sentence. Breaker and /ready state in a second PR.

**Spike.** Already run: scratchpad/spike_corrupt.py — nine injections (truncated index, deleted _indices, half data fragment, deleted data, deleted _versions, overwrite-under-read, readiness-after-corruption, rename swap) with the exact exception class and message for each. Rerun offline in ~2 s.

## `resilience-4` — Admission control: a small in-process search gate with a queue wait, so a hammering model gets 'busy' text instead of taking the server down

**pending (0/3 verdicts in) · effort S · impact 4/5**

**What the code does today.** tools.py:73-75 explains the threadpool is real concurrency ('64 simultaneous first calls built 16 separate facades'); nothing bounds it below anyio's 40 (anyio/_backends/_asyncio.py:3162). df_tool.py:106 caps `limit` at 100 and :167 caps `fuzzy` at 2, but neither bounds the number of terms, the number of concurrent calls, nor the total in-flight work. Measured (scratchpad/spike_hammer.py, 200k-row table, today's search path): 32 concurrent 8-word OR searches → wall 12.9 s, median latency 10.1 s, RSS +2.3 GB; a single cheap query behind them took 281 ms vs ~10 ms idle. On a 4-CPU host the threadpool's 40 slots are 10× the cores, so admitting 40 heavy searches only buys latency and memory. The HTTP transport has no auth (second audit, finding 11), so on a hosted endpoint this is reachable by anyone.

**The gap.** Under load the server degrades for everyone at once (latency, then OOM), and a well-behaved second user pays for a badly-behaved first. There is no signal — to the model, to /ready, or to a metric — that the server is saturated rather than slow.

**The proposal.** In dataset.py add a module-level `_gate = threading.BoundedSemaphore(SEARCH_CONCURRENCY)` with `SEARCH_CONCURRENCY = max(2, os.cpu_count() or 2)` (override `KA_SEARCH_CONCURRENCY`) and `QUEUE_WAIT = 2.0 s` (`KA_SEARCH_QUEUE_WAIT_SECONDS`); wrap the query execution at dataset.py:323-343 in `if not _gate.acquire(timeout=QUEUE_WAIT): raise SearchOverloadedError(...)` (a `SearchInputError` sibling so `_answer` returns its text): `Error: the server is busy (N searches in flight); wait a few seconds and retry the same query once.` Export an observable gauge `kansallisarkisto.lancedb.inflight` and counter `errors{error.type=overloaded}`. Because the gate lives in the lib, a standalone library user and the boot probe get the same protection; because the semaphore is bounded per process, memory is bounded at SEARCH_CONCURRENCY × per-call cost (≈4 × 70 MB today, ≈4 × 1 MB with resilience-2). `/ready` stays 200 when busy — busy is not broken.

**Why it is once-in-a-lifetime.** Backpressure expressed in the tool's own medium: a sentence a model can obey ('wait, retry once') rather than a 503 it never sees. Combined with resilience-1/2 it makes the worst-case per-process cost a product of three documented constants instead of an open question.

**How we would know.** Under the 32-way hammer, wall time drops from 12.9 s to ≤4 s for admitted calls, at most SEARCH_CONCURRENCY searches run concurrently (assert with a counting monkeypatch inside the gate), RSS growth ≤ SEARCH_CONCURRENCY × single-call cost, rejected calls return the busy sentence within QUEUE_WAIT + 50 ms, and an interleaved cheap query completes in <50 ms instead of 281 ms.

**Risks.** Rejecting a valid query is new behaviour for a server whose philosophy is 'every question answered'; the default is tuned so only pathological concurrency sees it, and stdio (one client) never does. A too-small gate on a many-core host would under-use lance's tokio pool — hence cpu_count, not a fixed 4. Does not replace an upstream rate limit on a public HTTP endpoint; it is the last line, not the first.

**First step.** One PR (~40 lines + 2 tests): the semaphore and `SearchOverloadedError` in dataset.py, the `_answer` branch, a test that fills the gate with a blocked monkeypatched `to_list` from N threads and asserts the (N+1)th call returns the busy sentence in ~QUEUE_WAIT.

**Spike.** Already measured the unguarded baseline in scratchpad/spike_hammer.py; the guarded run is the same script with a `threading.BoundedSemaphore(4)` around `lancedb_fts_search` — a 5-line edit.

## `resilience-5` — A bulletproof harvest: pin the plan, verify every slice against its own filter, write atomic parts, and make coverage arithmetic honest

**pending (0/3 verdicts in) · effort XL · impact 4/5**

**What the code does today.** harvest.py:294 replans from live counts on every run, including `--resume`; :289 loads only `done` keys; :304 takes whatever `/api/export-all` returns and :309-313 appends it and marks the slice done with no check that `len(hits)` equals the planned count or that the hits satisfy the slice filter — even though the module docstring (:35-42) itself records that a wrong `uiState` 'fails silently — the filter is ignored and the export returns an unfiltered page that looks perfectly valid'. :324 defines `complete` as 'no shortfalls', :329 computes `coverage_pct` from lines written over the index total. :173-196 retries 4 times with 1+2+4+8 s backoff and treats an HTTP 429/503 (an HTTPError, subclass of URLError) like any other failure — a 1.5 h tuomiokirjat run dies after 15 s of outage. ingest.py has no de-duplication by `object_id`. Measured with a stub service (scratchpad/spike_harvest.py, ceiling scaled to 100): (1) crash between append and checkpoint, then resume → 360 lines, 300 unique (the docstring's known window, now quantified); (2) index moved between runs so one year crossed the ceiling → resumed plan fetched `c=A|y=1600` and `c=B|y=1600` on top of the done `y=1600` → `coverage_pct: 119.15`, `complete: True`, verify exit 1; (3) service ignoring filters → `coverage_pct: 166.67`, `complete: True`; (4) every export 5 short → verify exit 0, `complete: True`, `coverage_pct: 91.67` — a short file with a clean bill of health. data-sources.md documents that `voudintilit` moved 99,031 → 99,125 between harvests, so case (2) is the normal case for a resumed run, not an edge.

**The gap.** Resume is unsafe against the one thing that always happens (the index moving), the report can claim completeness it does not have, and the only defence — `--verify` on objectID uniqueness — is blind to a short or unfiltered slice. For a 7.8M-document, 1.5 h harvest that feeds the largest table, this is the pipeline's weakest link.

**The proposal.** Rewrite `harvest_index` around a pinned plan and verified parts: (a) `plan.json` written once by `plan_slices` with `{index_total, harvested_at, slices:[{key, year, collection, documents}]}`; `--resume` loads it and never replans; `--replan` diffs a fresh plan against the pinned one and fetches only new/changed cells, recording the old ones as superseded. (b) Each slice is written to `parts/<sha1(key)>.jsonl.gz` via temp file + fsync + `os.replace`; the checkpoint entry becomes `{key, documents, bytes, sha256}` and is itself written atomically. The crash window between append and checkpoint disappears: a part exists complete or not at all; `<index>.jsonl.gz` becomes a concatenation step (`--assemble`) or `_open_jsonl`/ingest learns to read `parts/`. (c) Post-conditions before a slice is marked done: `len(hits) == min(slice.documents, EXPORT_CEILING)`; every hit's `alkuvuosi` equals `slice.year` and its collection facet equals `slice.collection` when set (this is exactly the silent-unfiltered-page failure the docstring warns of); objectIDs unique within the slice. A failing slice is retried once, then recorded as `failed` with the reason, never as done. (d) `report.complete = (unique_documents == index_total and not shortfalls and not failed)`, `coverage_pct` from unique objectIDs and capped at 100, with `duplicates` and `short_slices` fields. (e) `_post`: honour `Retry-After` and treat 429/503 as backoff, 8 attempts with jitter capped at 60 s, so a 5-minute outage is survived. (f) ingest: dedupe by `object_id` in `_df_batches` (a `set` of 7.8M ids ≈ 600 MB is too much — use the plan: parts are disjoint by construction, so dedupe only across superseded parts) or `merge_insert('object_id')`. (g) `--verify` checks parts against the checkpoint's sha256 and the plan's counts, so verifying a resumed run is a hash walk, not a re-read of 6.3 GB.

**Why it is once-in-a-lifetime.** The harvest becomes reproducible and provable: a pinned plan is a citable statement of what was asked of the service on a given day, each part carries its own hash and post-condition, and 'complete' means complete. That is what a historian citing a corpus snapshot and the next corpus's week-long port both need.

**How we would know.** The four stub scenarios in spike_harvest.py, ported to tests: (1) crash-then-resume yields exactly 300 unique lines and 300 total; (2) the moved-index resume fetches only the two new cells and reports coverage ≤100 with `superseded: ['y=1600']`; (3) the filter-ignoring service produces zero done slices and `failed: 3`; (4) the short service reports `complete: false, short_slices: 3`. `--verify` on a 6.3 GB tuomiokirjat harvest completes in seconds (hash walk) rather than a full decompress.

**Risks.** A rewrite of the largest script, testable only against a stub here (no network to the service); the per-hit filter check assumes the export returns `alkuvuosi` and the collection attribute on every hit — verify on the July 2026 files before relying on it. Parts change the on-disk layout documented in data-sources.md and the Makefile's `verify-data`. Pinning the plan means a resumed run deliberately ignores documents added since the plan — correct, but it must be said in the report (`plan_age`).

**First step.** PR 1 (a day): post-conditions (c) and honest `complete`/`coverage_pct` (d) in the existing loop, plus the stub-client test harness from spike_harvest.py as `scripts/tests/test_harvest.py`. PR 2: pinned plan and atomic parts. PR 3: retry policy and ingest dedupe.

**Spike.** Already run: scratchpad/spike_harvest.py and spike_harvest4.py drive scripts/harvest.py's real `harvest_index`/`verify` against an in-memory Sisältöhaku stub with the ceiling scaled to 100 — no network. Rerun: `/tmp/uvenv/bin/uv run --project /home/user/kansallisarkisto-mcp python spike_harvest.py`.

## `resilience-6` — Prove the swap: pin lance's atomic commit under disk-full, ship a blue/green table swap, and stop unbounded version retention on re-ingest

**pending (0/3 verdicts in) · effort S · impact 3/5**

**What the code does today.** ingest.py:144 uses `create_table(..., mode='overwrite')` into the live database; scripts/ingest_df.py:36-41 writes straight into the resolved URI (the served `data/` or `/data`) and never calls `cleanup_old_versions` or `compact_files`. deployment.md:70-72 says only 'indexes are baked in at ingest time and the served copy is read-only' — nothing about how a served table is replaced. Measured (scratchpad/spike_diskfull.py, spike_corrupt.py): a re-ingest interrupted by a 6 KB `RLIMIT_FSIZE` (`LanceError(IO): File too large (os error 27)`) left the table at version 7 with all six indexes and `search OK total=7` — lance's manifest commit is atomic, so a half-written ingest never breaks the served version (a property the project relies on and nowhere states or pins); three consecutive overwrites of the 18-row fixture retained 28 versions and all old data files (0.40 MB for one 0.13 MB table) — for tuomiokirjat (~19 GB of text) every re-ingest into a live directory adds another full copy until the disk is full, and a full disk turns the next commit into the failure just measured; a reader looping on a cached connection saw 0 errors across 3 overwrites (old versions keep serving); and renaming a freshly built directory over the old one under a cached connection served the new table immediately (`open_table` per call re-reads the manifest).

**The gap.** The safe deployment sequence exists by accident and is undocumented, and the unsafe one (`make ingest-df` into the served directory, repeatedly) grows disk without bound. Nothing tests either.

**The proposal.** Two tests in test_ingest.py: `test_interrupted_ingest_leaves_the_previous_version_serving` (subprocess with `resource.setrlimit(RLIMIT_FSIZE, 6000)` — the exact recipe from the spike, ~1 s) and `test_directory_swap_by_rename_is_seen_by_a_cached_connection`. In `ingest_df`, after the indexes: `table.cleanup_old_versions(older_than=timedelta(0), delete_unverified=True)` guarded by a new `retain_versions: bool = False` parameter — default off for a *fresh* directory (nothing to clean), documented as unsafe to run against a directory a server is currently serving. Make `scripts/ingest_df.py` build into `<uri>.new`, run the boot-style probe against it, then `os.replace` it over `<uri>` (blue/green), refusing to build into a directory that already holds a table unless `--in-place`. Document in deployment.md: mount the *parent* directory so the swap is a rename inside the mount, and state the disk arithmetic (2× the table during a swap, never 3×).

**Why it is once-in-a-lifetime.** The one operational sequence every archive operator performs — replace the corpus under a running server — becomes a tested, one-line, atomic operation with a stated disk budget, instead of folklore about what lance happens to tolerate.

**How we would know.** Both tests pass in CI in <3 s; three consecutive `make ingest-df` runs leave exactly one table version and on-disk size within 5% of a single fresh ingest (today 28 versions / ~3×); a server serving during the swap logs zero errors and answers the smoke test's `konung` query before and after; `deployment.md` gains the swap section and the second audit's stale `"table"` key example is corrected on the way.

**Risks.** `cleanup_old_versions` against a directory another process is reading can delete a version that reader is on — hence default off and blue/green by rename as the recommended path. `os.replace` of a directory onto a non-empty directory fails on POSIX; the script must rename old → `.old`, new → live, then delete `.old`, and say so. The `KA_LANCEDB_URI=/data` bind-mount story in the Dockerfile (line 72) needs the parent-directory note or the rename crosses a mount boundary and fails.

**First step.** PR: the two tests (they document the properties even before any code changes) and the `cleanup_old_versions` call with the guard; the blue/green script change in a follow-up.

**Spike.** Already run: scratchpad/spike_diskfull.py (RLIMIT_FSIZE 6 KB → `File too large (os error 27)`, version 7 still serving) and spike_corrupt.py sections 7 and 9 (0 reader errors across 3 overwrites, 28 versions retained; rename swap served immediately).

## `resilience-7` — Keep the telemetry stack's own failures out of the application's error signal

**pending (0/3 verdicts in) · effort S · impact 3/5**

**What the code does today.** telemetry.py:116-119 attaches `_MetricsLoggingHandler` to the root logger at WARNING, counting every WARNING+ record into `kansallisarkisto_mcp.log.messages{log.level}` — the metric observability.md:94 describes as the error-rate panel; telemetry.py:140 attaches the OTLP `LoggingHandler` at NOTSET to the same root logger. Measured (scratchpad/spike_otel_loop.py) with `KA_MCP_OTEL_ENABLED=true` and the endpoint pointed at a refusing port: search latency was unaffected (median 6.6 → 7.1 ms, so the audit's bounded-shutdown fix and the batch processors hold), but in 12 s of a perfectly healthy server the `opentelemetry.exporter.otlp.proto.grpc.exporter` logger emitted 6 ERROR and 5 WARNING records versus 0 from the application — every one counted into `log.messages{ERROR}` and every one handed back to the failing `LoggingHandler` for export, which fails and logs again. `BatchSpanProcessor` silently drops beyond its 2,048-span queue (observed `_max_queue_size: 2048`, queue at 352 after 12 s) and nothing surfaces the drop.

**The gap.** With the collector down, the error-rate panel shows ~0.5 errors/s from a healthy server, indistinguishable from real faults, and the log bridge amplifies its own failure. The one time an operator most needs the error metric to be trustworthy — infrastructure trouble — it is not.

**The proposal.** Add a `logging.Filter` that drops records whose `name` starts with `opentelemetry.` and install it on both handlers (`_MetricsLoggingHandler` and `LoggingHandler`); route those records instead to a `kansallisarkisto_mcp.telemetry.export_failures{signal=traces|metrics|logs}` counter via a tiny dedicated handler on the `opentelemetry.exporter` logger, rate-limited to one stderr line per minute per signal. Set `OTEL_EXPORTER_OTLP_TIMEOUT` default to 5 s in `init_telemetry` if unset (the SDK default is 10 s and retries stack). Document in observability.md a 'collector down' row: what you will and will not see (spans dropped past 2,048, metrics delayed, application metrics intact).

**Why it is once-in-a-lifetime.** The observability layer is already unusual in marking text-returned errors on spans; making it immune to its own outage completes the promise that the error metric means application errors and nothing else.

**How we would know.** Re-running spike_otel_loop.py after the change: 0 WARNING+ records reach `_MetricsLoggingHandler` from `opentelemetry.*` in 12 s (today 11); `telemetry.export_failures` increments instead; stderr carries ≤1 exporter line per minute per signal (today ~1 every 1–2 s); a test with the endpoint at 127.0.0.1:1 asserts `log.messages{ERROR}` stays 0 across 50 searches.

**Risks.** Filtering a logger by name prefix hides genuine SDK misconfiguration from the log stream; the rate-limited line and the counter are the replacement, and the filter must not touch the stderr `basicConfig` handler so a laptop user still sees the first failure. Pure MCP-package change; the lib's API-only stance is untouched.

**First step.** One PR: the filter class, two `addFilter` calls, the counter handler, one test using the in-memory metric reader pattern from test_telemetry.py.

**Spike.** Already run: scratchpad/spike_otel_loop.py — counts log records by (logger, level) over 12 s with a refusing collector (11 from opentelemetry.*, 0 from the app; latency unchanged). Offline, ~15 s.

## `resilience-8` — Fault injection as a test discipline: a `faults` fixture family that builds each failure from the 18-row fixture and asserts the documented behaviour at all three surfaces

**pending (0/3 verdicts in) · effort M · impact 4/5**

**What the code does today.** The suite fakes failures by monkeypatching a method to raise (`test_tools.py:92-104` raises a RuntimeError with a fake lance path; `test_server.py:88-104` substitutes an `Unreadable` class). No test builds a genuinely broken table, a stalled query, a full disk, a refusing collector or a disconnecting stdio client — yet every one is reproducible offline in milliseconds to seconds, as the spikes under the scratchpad show (truncate `_indices/*/*` to 0 bytes; delete `_indices/`, `data/` or `_versions/`; truncate a data fragment to half; `RLIMIT_FSIZE` in a subprocess; endpoint `127.0.0.1:1`; a stdio subprocess whose stdin is closed mid-call). The behaviour under each is currently whatever falls out of `_answer`'s `except Exception` (df_tool.py:51) — the same sentence for all — and nothing pins that /ready, the tool text and the `error.type` label agree for a given fault.

**The gap.** Resilience claims in this repository are prose (deployment.md's ownership paragraph, tools.py's 'never raises' docstrings) verified by hand once; the retrieval-quality suite showed what pinning a class of failure buys, and there is no equivalent for operational failure.

**The proposal.** Add `packages/kansallisarkisto-lib/tests/faults.py` (a conftest plugin) with fixtures parametrised by kind: `broken_table(kind)` for `index-truncated | index-missing | data-truncated | data-missing | versions-missing`, built by ingesting df_sample into tmp_path and applying the recipe; `stalled_query(seconds)` monkeypatching `lancedb.query.LanceQueryBuilder.to_arrow` to sleep before delegating (the slow-filesystem shim, honouring a passed `timeout` so deadline tests are real); `disk_full` running a callable in a subprocess under `RLIMIT_FSIZE`; `refusing_collector` setting the OTLP env to a closed port; `stdio_server(tool)` returning a subprocess with a JSON-RPC helper for the disconnect case. Then one parametrised test per surface: `test_tool_text_per_fault` (exact sentence prefix from resilience-3), `test_ready_per_fault` (status code + class), `test_error_type_per_fault` (span attribute via the in-memory exporter already used in test_telemetry.py), plus `test_deadline_returns_text_not_protocol_error`, `test_gate_rejects_the_nth_call`, `test_interrupted_ingest_keeps_serving`, `test_stdio_disconnect_exits_within_deadline`. Generate observability.md's failure matrix from the parametrisation ids so the table cannot drift from the tests (the same trick the second audit's finding 6 used for the fixture count).

**Why it is once-in-a-lifetime.** It makes every sentence in the deployment and observability pages an executed assertion built from real broken bytes, on the same 18-row fixture, in seconds — the operational counterpart to test_retrieval_quality.py, and the thing that lets a maintainer upgrade lancedb and know within one CI run whether an error string or a crash-safety property changed.

**How we would know.** ≥12 new tests, each <2 s, all offline; CI fails if any of the five lance error strings changes wording; the failure matrix in observability.md is generated, with a test asserting the page matches; coverage of df_tool.py's `_answer` branches and tools.py's readiness paths reaches 100% by fault kind rather than by mock.

**Risks.** Substring-based classification and byte-level corruption recipes are coupled to lance's on-disk layout (`_indices/<uuid>/tokens.lance`, `data/*.lance`, `_versions/*.manifest`); a layout change breaks the fixtures loudly, which is the intent, but someone must then re-derive the recipes. The stdio subprocess test adds ~6 s unless the sleep is shortened to 1 s. Running as root in some CI containers makes the mode-0600 permission case unreproducible (the spike hit this: euid 0 ignores mode bits) — that one stays a documented manual check or uses a uid-switching subprocess.

**First step.** PR: `broken_table` fixture with the five recipes and a single parametrised test asserting today's behaviour verbatim (the exact `RuntimeError`/`ValueError` messages from spike_corrupt.py) — a characterisation test that resilience-3 then updates to the new sentences.

**Spike.** Already run: scratchpad/spike_corrupt.py, spike_diskfull.py, spike_otel_loop.py, spike_stdio_disconnect.py (with stdio_slow_server.py) are the fixtures in prototype form; each ran offline in 1–15 s against the 18-row fixture.
