## `perf-1` — One ranking, twenty-five rows: rank on _rowid+_score, page with take_row_ids

**pending (0/3 verdicts in) · effort M · impact 5/5**

**What the code does today.** dataset.py:290 opens the table per call; :307-309 projects every column except FTS_COLUMN plus _score; :326 `matches = query.limit(MAX_TOTAL_COUNT).to_list()`; :336-337 counts and slices the page in Python. The docstring at :249-255 justifies dropping the FTS column (6.1 MB -> 3.3 MB) but still materialises up to 10,000 full rows as Python dicts. Measured on the 18-row fixture replicated x3000 (54,000 rows; 'Åbo' capped at 10,000 hits, warm cache, 4 CPUs): open_table 0.48 ms, schema.names 0.24 ms, `to_list` full projection 105 ms p50 / 117 p90; `to_arrow` of the same 35 ms (so ~70 ms is Arrow->dict conversion holding the GIL); projection without transcript 80 ms; `select(['_score']).with_row_id(True).to_arrow()` 10.6 ms and 120 KB; `limit(25)` full 6.8 ms; Python slice 0.00 ms; format_search_results 0.04 ms. The 10k Arrow page-set is 5.0 MB, 72% transcript. RSS over 200 capped queries through DfSearch.search: 145 -> 233 MB after one query, 451 after 25, 715 after 150, 632 after gc (allocator retention of 10k x 15-key dict pages); the narrow variant stays flat at 194 MB. Same table at x30000 (540,000 rows): full 110 ms, ranking-only 16.9 ms. Also verified: on this tie-heavy table a separate `limit(25)` does NOT equal the first 25 of `limit(10000)` and `offset(25).limit(25)` does not equal slice[25:50] — the docstring's tie-reorder concern (:244-247) is real — while re-running the same 10k query is stable, and `Table.take_row_ids` exists but returns rows in storage order, not request order.

**The gap.** A capped query costs ~100 ms and 5 MB of Arrow plus ~50 MB of transient Python objects to learn a total of '10000+' and return 25 rows; 2/3 of the time is GIL-held dict building that also serialises every concurrent query (see perf-5). At tuomiokirjat page sizes (19 GB / 7.8M ≈ 2.4 KB of text per row) the same code materialises ~25 MB of Arrow and hundreds of MB of dicts per query per worker thread.

**The proposal.** In `lancedb_fts_search` (dataset.py:290-352) keep exactly one ranked query but make it narrow, then fetch the page by row id: ```python ranked = query.select(["_score"]).with_row_id(True).fast_search().limit(MAX_TOTAL_COUNT).to_arrow() # ~120 KB total = ranked.num_rows page_ids = ranked["_rowid"][offset:offset + limit].to_pylist() page_scores = ranked["_score"][offset:offset + limit].to_pylist() rows = table.take_row_ids(page_ids).select(columns).with_row_id().to_list() if page_ids else [] by_id = {r.pop("_rowid"): r for r in rows} page = [{**by_id[i], "_score": s} for i, s in zip(page_ids, page_scores)] # restores ranking order; take_row_ids does not ``` `where` stays on the ranking query so total and page remain over the filtered set. Record shape is unchanged (formatter.py untouched). Cache the `Table` handle and column list on `DfSearch` (search_operations.py:26-28, :129-130) — open_table+schema is 0.7 ms, i.e. 5% of the new budget, and one manifest read per query on object storage. Do the same in `get_charter` (:129-131). Add `test_page_rows_come_back_in_ranking_order` beside `test_pages_tile_the_result_set_without_gaps_or_repeats` (test_search_invariants.py:133) because take_row_ids reorders. Measured two-step cost: 13.5 ms p50 at 54k rows, 20.0 ms at 540k (deep offset 9,975: 16.0 / 21.6 ms).

**Why it is once-in-a-lifetime.** It turns the engine's missing count API from a 100 ms / 5 MB tax into a 10 ms / 120 KB one without giving up the single-ranking invariant the project argued for, and it is the change that makes 'scales to 7.8M pages without changing shape' true: the per-query working set becomes independent of transcript size. It also removes the biggest GIL holder in the process, which is why perf-5's numbers move.

**How we would know.** On the x3000 replica: capped df_search p50 <= 20 ms (from 105); VmRSS after 200 capped queries <= 220 MB (from ~630); in-memory FastMCP Client throughput at concurrency 4 >= 60 calls/s (from 10.6); every existing invariant test green, plus the new ranking-order test. The docstring's '6.1 MB to 3.3 MB' sentence is replaced by a number the benchmark suite re-derives.

**Risks.** `_rowid` is stable only while no compaction/update happens between ranking and take; the tables are build-once (dataset.py:312-314) but perf-6's cleanup/optimize must run in the ingest path only. `take_row_ids` on a row deleted between the two calls raises — wrap and treat as a transient. The sync take builder takes `with_row_id()` with no argument while the FTS builder takes `with_row_id(True)`; pin both against the lancedb version. lancedb warns that `_score` auto-projection will stop; selecting it explicitly (as here) is the future-proof form.

**First step.** One PR: implement the two-step in `lancedb_fts_search`, cache the table handle in `DfSearch`, add the ranking-order test, and update the projection docstring with the measured before/after. ~60 lines changed.

**Spike.** Ingest the fixture into a temp LanceDB with `ingest_df`, replicate it x3000 by rewriting `df`/`objectID` per copy, then time (15 reps, p50) `tbl.search(MatchQuery('Åbo', column='searchable_text', operator=AND), query_type='fts').select(cols+['_score']).fast_search().limit(10000).to_list()` against `select(['_score']).with_row_id(True)...to_arrow()` + `tbl.take_row_ids(ids[:25]).select(cols).to_list()`, and sample /proc/self/status VmRSS every 25 queries for 200 queries in both modes. Expected: ~105 vs ~13 ms; ~630 vs ~194 MB.

## `perf-2` — Answer `initialize` before lancedb is imported: lazy engine imports and a background boot probe, pinned by a test

**pending (0/3 verdicts in) · effort S · impact 4/5**

**What the code does today.** dataset.py:20-21 import `lancedb.index` and `lancedb.query` at module top, which defeats the deliberate lazy `import lancedb` inside `get_lancedb` (dataset.py:118): `import ra_mcp_kansallisarkisto_mcp.tools` puts `lancedb` and `lance_namespace_urllib3_client` in sys.modules (verified). server.py:218 runs `log_table_status()` (and the one-row probe, :191) before `run()` at :224/:231, so nothing is read from stdin until the whole import tree and the probe are done. Measured with `-X importtime`: server import tree 2.3 s; `lancedb` 1.0-1.15 s, of which 831 ms self-time is `lance_namespace_urllib3_client` (a 41,232-line generated REST client with 148 model modules, imported unconditionally by lancedb/db.py:35 and never used by a local table); fastmcp 455 ms + mcp 267 ms (the server imports `mcp.client.session`, 158 ms). Floor without lancedb (fastmcp + pydantic_settings + otel API + pyarrow): 540-610 ms. Real stdio session via `fastmcp.Client(StdioTransport)`: spawn -> initialize 1.58-1.87 s; tools/list 5 ms; first df_search 22-37 ms on 18 rows, 201 ms on 540k rows; connect 3 ms; list_tables 1 ms. So ~90% of time-to-first-answer is imports, and half of those are for a feature this server cannot use.

**The gap.** A laptop stdio client waits ~1.7 s for the handshake, and the design comment 'stdio on a laptop must cost nothing' is not measured anywhere. The lazy connection in `get_lancedb` is a good idea that a later import silently undid — exactly the kind of drift this codebase pins elsewhere (test_search_invariants.py:42-56 asserts the index config against the built index).

**The proposal.** (1) Move `from lancedb.index import FTS, Bitmap, BTree` into `build_fts_index`/`build_scalar_indexes` and `from lancedb.query import FullTextOperator, MatchQuery` into `lancedb_fts_search` (function-local imports are a dict lookup after the first call). (2) In `server.main()` start `log_table_status()` on a daemon thread after logging/telemetry setup so FastMCP starts reading stdin immediately; `get_search()` already serialises first use with a lock (tools.py:293), so a tool call arriving mid-import simply waits. (3) Pin it: `test_importing_the_server_does_not_import_lancedb` runs `python -c "import ra_mcp_kansallisarkisto_mcp.tools, sys; assert 'lancedb' not in sys.modules"` in a subprocess, and `bench_coldstart` (perf-3) records spawn->initialize. (4) File the upstream lancedb issue with the number: eager `lance_namespace` import costs 830 ms on every local-only process; ask for a lazy import in `lancedb/db.py`. (5) Record in df_tool.py's module docstring that `-X importtime` inflates by ~30% and the real handshake floor is fastmcp's ~0.6 s.

**Why it is once-in-a-lifetime.** It makes the stated laptop promise true and measured: the handshake drops to fastmcp's floor and the engine loads during the seconds-to-minutes a human spends before the first question. It is also the first time a project of this kind will have quantified where a stdio MCP server's cold start actually goes and sent the fix upstream rather than absorbing it.

**How we would know.** spawn -> initialize <= 0.8 s (from 1.6-1.9 s) on the same machine; `lancedb` absent from sys.modules after importing `tools`; first df_search after a cold spawn unchanged (<= 40 ms on the fixture); an upstream lancedb issue number recorded in docs/development/index.md.

**Risks.** The background import competes for the GIL with the handshake — but the handshake is milliseconds of Python and the import is 1 s, so the overlap is with client latency, not a free lunch. A tool call that arrives during the import pays the full second once (same as today, just later). The test must run in a subprocess because pytest's own fixtures import lancedb. If a future FastMCP reads stdin before `run()`, step 2 becomes redundant, not harmful.

**First step.** One PR: the two import moves, the daemon-thread boot probe, the subprocess test, and a sentence in the df_tool docstring; then the upstream issue.

**Spike.** `python -X importtime -c 'import ra_mcp_kansallisarkisto_mcp.server' 2>imp.txt` then sort column 2 — lance_namespace_urllib3_client ~830 ms self, fastmcp ~455 ms. `python -c 'import sys, ra_mcp_kansallisarkisto_mcp.tools; print("lancedb" in sys.modules)'` -> True today. Time `fastmcp.Client(StdioTransport(command='uv', args=['run','--no-sync','kansallisarkisto-mcp'], env={'KA_LANCEDB_URI': <fixture db>}))` from construction to `__aenter__` return: ~1.7 s.

## `perf-3` — A benchmark suite CI gates on: replicated fixture at a scale knob, p50/p99 per tool through the in-memory client, RSS, import time, ingest rows/s and index build

**pending (0/3 verdicts in) · effort L · impact 5/5**

**What the code does today.** There is no performance measurement anywhere in the repository: .dagger/test.go runs `pytest -q` only; the Makefile has no bench target; ci.yml runs checks/test/test-mcp/test-server. Every number in the code comments (6.1 MB -> 3.3 MB at dataset.py:252, 'cheap after the first call' at tools.py:319-321, 'a few milliseconds on a mounted table' in audit finding 1) was measured once by hand and is unverified since. The only in-repo data is 18 rows (conftest.py:249-254); corpus-only tests are gated on `.data/df/df.jsonl.gz` (test_search_invariants.py:215-216) and skip in CI. conftest.py:276-278 makes `df_table` function-scoped, so each of the ~100 search tests re-ingests and rebuilds five indexes (the 10 s suite is mostly ingest). Measured facts the suite would have caught: capped query 105 ms with 70 ms of dict building; RSS 145 -> 715 MB over 150 queries; throughput 13 q/s flat from 1 to 8 threads; import 2.3 s; index-build peak RSS 991 MB at 540k rows; ingest 27.6-34.7k rows/s. pytest-benchmark 5.3.0 installs on Python 3.14.7 (verified).

**The gap.** The project's method is 'measure, then write the number next to the code' — but the numbers are frozen prose. A regression in any of them (a lancedb bump changing `to_list` cost, a projection change, a new eager import) is invisible until an operator notices.

**The proposal.** Add `packages/kansallisarkisto-lib/benchmarks/` (excluded from the default pytest run via `--ignore`, selected by `make bench`): - `conftest.py`: session-scoped `scaled_db` built by `replicate_fixture(n)` — a helper in `ra_mcp_kansallisarkisto_lib.testing` that rewrites `df` to 1..18n and suffixes `objectID`, writes JSONL, and runs the real `ingest_df`. `KA_BENCH_SCALE` default 3000 (54k rows, ~4 s to build; every fixture term is capped at 10k except single-row terms at 3,000 hits, so both branches of `total_is_capped` are exercised). - `bench_search.py`: scenarios {capped 'Åbo', uncapped single-row term, every-doc 'df', AND vs OR 'konung Åbo', phrase '"de ecclesia"', fuzzy=1 'Åbo' and 'bref', filters: bitmap equals, btree year overlap, LIKE issuingplace, deep offset 9975, get_charter}, each direct via `DfSearch` and via `fastmcp.Client(kansallisarkisto_mcp)` in-memory (includes pydantic validation, threadpool hop, formatter; measured dispatch overhead 5-6 ms). Report p50/p99 over 200 calls. - `bench_ingest.py`: rows/s for parse+create_table, FTS build seconds, scalar seconds, `ru_maxrss` delta, on-disk bytes per row (data vs _indices), at scale. - `bench_memory.py`: VmRSS delta after 100 capped queries (tracemalloc cannot see Arrow). - `bench_coldstart.py`: subprocess `-X importtime` total and lancedb subtree; spawn->initialize via StdioTransport; first query after `os.posix_fadvise(fd,0,0,POSIX_FADV_DONTNEED)` over the table files (measured 215 vs 99 ms warm at 540k). - `bench_contention.py`: q/s at 1/4 threads and ms/query beside a CPU-bound Python thread (perf-5). Numbers: pytest-benchmark `--benchmark-json` -> `benchmarks/results/<sha>.json` as a workflow artifact; a committed `benchmarks/baseline.json` regenerated by `make bench-baseline`. Gates that survive noisy runners: pytest-benchmark `--benchmark-compare-fail=median:50%` on absolutes (loose, min-of-3-rounds), plus hard machine-independent ratios asserted in code: RSS growth < 50 MB per 100 queries; capped-query time / ranking-only time < 2; `lancedb` share of import < 60% until perf-2 lands then `lancedb not in sys.modules`; index-build peak RSS per MB of text < a stated constant. Run in a Dagger `Bench` function (`.dagger/bench.go`) on PRs touching dataset.py, ingest.py, search_operations.py, df_tool.py, formatter.py or uv.lock (paths filter), and nightly on main appending to a `benchmarks` branch that `docs/development/performance.md` renders — the same measured-numbers-next-to-code style, now regenerated. Side benefit: make `df_table` session-scoped for read-only tests and the unit suite roughly halves.

**Why it is once-in-a-lifetime.** Archival MCP servers do not ship benchmark suites; this one would carry its measured claims as executable assertions, so 'every design decision measured on the corpus' becomes a property of CI rather than of the author's memory. The next corpus gets its numbers for free by changing KA_BENCH_SCALE and the fixture.

**How we would know.** `make bench` produces a JSON with >= 20 named scenarios in < 3 min at scale 3000; CI fails a PR that reintroduces the full-projection `to_list` (median +400%, RSS +400 MB) or an eager lancedb import; `docs/development/performance.md` shows a per-commit history with at least import time, capped/uncapped p50/p99, ingest rows/s, index build s, peak RSS.

**Risks.** Runner noise: GitHub-hosted runners vary 2x, so absolute gates must be loose and the sharp gates must be ratios; Dagger adds container start time. The replicated fixture has a tiny vocabulary, so posting-list and term-dictionary costs are understated (perf-7 addresses fidelity). pytest-benchmark's stats machinery is heavier than needed — a 100-line harness writing the same JSON is a valid alternative and avoids a dev dependency.

**First step.** PR 1: `replicate_fixture(n)` helper + `bench_search.py` with five scenarios via DfSearch and the in-memory client, `make bench`, JSON output, no gate. PR 2: baseline + Dagger function + ratio gates. PR 3: ingest/memory/coldstart/contention files and the docs page.

**Spike.** Already runnable: replicate the fixture x3000 (writes 57.7 MB JSONL, ingests in ~3.5 s incl. FTS), then a loop timing `DfSearch.search` and `Client(kansallisarkisto_mcp).call_tool('df_search', ...)` for the scenario list, printing p50/p99 and VmRSS. Compare against x300 to see which scenarios scale with rows (every-doc 12.6 -> 31 ms, fuzzy 14.8 -> 65.7 ms, LIKE 16 -> 57 ms for x10 rows) and which do not (capped rank ~10 -> 17 ms).

## `perf-4` — The FTS index build is the one non-streaming step: bound it, measure it per row, and ship pre-built tables so operators never build

**pending (0/3 verdicts in) · effort L · impact 4/5**

**What the code does today.** ingest.py:271-279 streams the table write and its docstring (:276-277) says 'peak memory is one batch rather than the whole corpus' — true of the write only. ingest.py:281 then calls `build_fts_index` once over the whole table; dataset.py:169-191 configures `FTS(language, stem, remove_stop_words=False, with_position=True, ascii_folding, max_token_length=64)` — there is no memory, partition or worker knob on that config, and lance is bundled inside `lancedb._lancedb` with no pylance surface to reach one. Measured `ru_maxrss` for `build_fts_index` alone: 138 -> 298 MB at 54k rows (41 MB table), 138 -> 991 MB at 540k rows (274 MB data); the ~850 MB delta is ~2.3x the data bytes, with positions on. Build time 1.3 s and 10.9-12.9 s (linear so far). df's 6,876 rows are trivial; tuomiokirjat is 7,835,557 pages and 19 GB of text, so a linear extrapolation is ~40 GB of peak RSS on the ingest machine — more than the 15 GB laptop this was measured on and any GitHub runner. `mode='overwrite'` (:279) plus four `replace=True` index builds also mean a re-ingest leaves the previous data and index files on disk (see perf-6).

**The gap.** The project promises the three corpora share one shape; the ingest path is fine for df and voudintilit but has an unmeasured, unbounded memory step that would fail on the corpus that is 99% of the pages, and nothing says so.

**The proposal.** (1) Measure the slope: `bench_ingest` (perf-3) records peak RSS per MB of `searchable_text` at scales 300/3000/30000 and the docs state the formula and the machine class needed. (2) Find the lever, in order: check whether lancedb's FTS builder is per-fragment by ingesting with smaller fragments (lance `max_rows_per_file`, if reachable through `create_table` kwargs) and re-measuring peak; if not, try building the index per year-partitioned table and searching N tables from the spine merging by `_score` (argues against the single-table shape — record the trade-off); if neither, open the upstream issue with the measured slope and ask for a bounded/spilling inverted-index build. (3) Independently of the lever: publish the built table as a release artifact — `dagger call build-table` produces `df.lance` as a tarball (or OCI artifact) with its digest recorded in the release next to the SBOM, and `docs/development/deployment.md` documents mounting it, so the 'empty image + mounted table' story does not require every operator to own an ingest machine. (4) Turn the ingest docstring's memory claim into two sentences: write is one batch; index build is proportional to text, with the measured constant.

**Why it is once-in-a-lifetime.** It is the difference between 'the shape scales' as a belief and as a measured property with a published constant — and shipping the table as a verifiable artifact extends the project's supply-chain rigour (cosign, SLSA, SBOM) to the data, which no comparable archive server does.

**How we would know.** A published number 'peak RSS = a + b x text MB' with b measured at three scales within 20% of each other; a documented ingest for voudintilit (98,945 rows) that fits in 2 GB; either a bounded build path for 7.8M pages demonstrated at 1M synthetic rows under 4 GB, or an upstream issue plus a documented partition strategy; a `df.lance` artifact with a digest in the v0.2 release.

**Risks.** The constant comes from replicated text with a tiny vocabulary; real OCR text has a far larger term dictionary and more positions per document, so the true slope is probably worse, not better. Partitioning changes ranking (BM25 statistics per partition) and pagination semantics — it must not be adopted without the invariant tests running across partitions. Artifact size: ~4-6 GB for tuomiokirjat is fine for a release asset but not for a git-lfs habit.

**First step.** PR: `bench_ingest` peak-RSS-per-MB at three scales, the corrected ingest docstring, and a table in deployment.md; then the fragment-size experiment.

**Spike.** Rebuild the FTS index on the x300, x3000 and x30000 replicas with `build_fts_index(db, 'df')` and read `resource.getrusage(RUSAGE_SELF).ru_maxrss` before/after each (fresh process per scale): expect ~+160 MB, ~+850 MB and a linear fit; then re-create the x30000 table with smaller fragments if `create_table` accepts a rows-per-file option and see whether the peak moves.

## `perf-5` — Measure the threadpool ceiling and the GIL ping-pong: bound workers, shrink the switch interval, and record why the async API is not the answer

**pending (0/3 verdicts in) · effort S · impact 3/5**

**What the code does today.** df_tool.py:6-10 makes both tools sync so FastMCP runs them in a worker thread; FastMCP dispatches through `anyio.to_thread.run_sync` (fastmcp/utilities/async_utils.py:34) with anyio's default limiter of 40 concurrent threads; tools.py:290-293 already observed 64 simultaneous first calls. Measured on the x3000 replica: today's path 9.9 q/s at 1 thread and 13-14 q/s at 2/4/8 threads; through the in-memory FastMCP client 9.8-10.6 calls/s at concurrency 1-16; lancedb's native async API (`connect_async`, gathered coroutines) 10.4-12.7 q/s at concurrency 1-16 — no gain. Beside one CPU-bound Python thread (a spinner) the picture is dramatic: today's search 100 -> ~916 ms/query; the perf-1 two-step 11 -> 736 ms (65x); with `sys.setswitchinterval(0.0002)` 59 ms; async two-step 12 -> 571 ms beside the spinner and 4,364 ms/query beside an event loop running 2 ms Python slices. Mechanism: lancedb's sync API bounces every Rust future through its background event-loop thread, and every hop re-acquires the GIL, waiting up to the 5 ms switch interval whenever any Python thread is busy — and today's `to_list` (70 ms of pure Python per query) is exactly such a thread for every concurrent query, which is why throughput does not scale with threads. After perf-1 the two-step path scales to 76 q/s at 1 thread and 111 q/s at 4-8 threads (8.5x today).

**The gap.** The sync-in-threadpool decision is right but unmeasured, the per-process ceiling (~13 q/s today, ~110 after perf-1 on 4 cores) is unknown to operators, 40 in-flight queries can each hold 5-25 MB of Arrow, and any busy Python thread in the process (OTel BatchSpanProcessor export, another query's formatting) degrades every search 10-60x.

**The proposal.** (1) In `server.main()`: `sys.setswitchinterval(0.0005)` with the measured justification (736 -> ~59 ms under contention; no cost when idle — verify FastMCP throughput is unchanged in `bench_contention`). (2) Cap the worker pool: `anyio.to_thread.current_default_thread_limiter().total_tokens = min(8, os.cpu_count())` inside the running loop (a FastMCP lifespan hook), and document the memory bound per in-flight query (120 KB ranking + one page after perf-1). (3) Add `bench_contention` (perf-3) with three lines: q/s at 1/4 threads, ms/query beside a spinner, ms/query via the async API — so the df_tool docstring's decision is pinned by numbers, not prose. (4) Record in df_tool.py that the async API was measured and rejected: equal throughput, worse under a busy loop. (5) HTTP only, later and XL if a hosted endpoint ever exists: a query worker process (one lancedb connection per process, `multiprocessing` with Arrow IPC) removes the GIL from the search path entirely — argue against enabling it for stdio, where a second process contradicts 'costs nothing on a laptop'.

**Why it is once-in-a-lifetime.** It replaces a plausible docstring with the measured concurrency model of a Rust-engine-under-CPython MCP server — including the counter-intuitive result that the vendor's async API does not help — and gives operators a real capacity number per core.

**How we would know.** bench_contention shows two-step search <= 80 ms/query beside a spinner (from 736) after the switch-interval change and >= 100 q/s at 4 threads on the replica; in-flight worker threads never exceed the cap under a 64-way `asyncio.gather` through the in-memory client; the docstring in df_tool.py cites the numbers.

**Risks.** A smaller switch interval raises context-switch overhead for genuinely CPU-bound Python; the server has almost none, but measure fastmcp's own JSON path before and after. Changing anyio's limiter is a global for the process (fine here, it owns the process). The worker-process idea doubles memory for the table's page cache and changes the failure model; it is an HTTP-only option and must stay off for stdio.

**First step.** One PR: switch interval + limiter cap in `main()` with comments quoting the measurements, plus the bench_contention scenario.

**Spike.** On the x3000 replica, run 10 two-step searches alone (~11 ms each), then with `threading.Thread(target=lambda: busy-loop)` alive (~700 ms each), then again after `sys.setswitchinterval(0.0002)` (~60 ms); repeat via `lancedb.connect_async` inside `asyncio.run` with a coroutine doing 2 ms busy slices between `await asyncio.sleep(0)` (seconds per query).

## `perf-6` — Ingest leaves every previous version and index on disk: cleanup and compaction at the end of ingest_df

**pending (0/3 verdicts in) · effort S · impact 2/5**

**What the code does today.** ingest.py:279 `create_table(..., mode='overwrite')` creates a new dataset version rather than deleting the old files; :281-287 then run five `create_index(..., replace=True)` calls, each another version; nothing in `ingest_df` or scripts/ingest_df.py:36-42 calls `Table.cleanup_old_versions` or `Table.optimize` (both exist on the sync `LanceTable`: `optimize(cleanup_older_than=, delete_unverified=, retrain=)`). Measured: re-running the fixture ingest into the same database twice grows `df.lance` from 224 KB to 624 KB with 21 versions in `_versions/`; rebuilding the FTS index on the 540k replica doubled `_indices/` from 83 MB to 166 MB. At df scale this is invisible; at tuomiokirjat (274 MB data + 83 MB index per 540k replicated rows, so several GB per version) a re-harvest triples the mounted volume, and `open_table` walks the version list on every query (dataset.py:290).

**The gap.** The harvest is designed to be re-run (scripts/harvest.py is resumable; audit finding 6 assumes re-ingest), but every re-run silently keeps the previous corpus on disk, and the docs never say to clean up.

**The proposal.** At the end of `ingest_df`, after the last index build: `table.optimize(cleanup_older_than=timedelta(0), delete_unverified=True)` and return the re-opened handle; log the `CleanupStats` (bytes removed, versions removed). Guard it with the comment already at dataset.py:214-216: builds mutate the dataset and belong in the ingest path, never against live data — cleanup in particular deletes files a running server may have open. Test in test_ingest.py: ingest the fixture twice into one db; assert on-disk bytes after the second run <= 1.05x after the first, and `test_nothing_is_left_unindexed` stays green. Add `--keep-versions` to scripts/ingest_df.py for the debugging case.

**Why it is once-in-a-lifetime.** Small, but it is the difference between an operator re-harvesting monthly and an operator discovering a full disk; it also makes perf-4's shipped table artifact minimal by construction.

**How we would know.** Directory size after two consecutive ingests within 5% of one ingest; `len(table.list_versions())` small and constant across re-runs; the deployment page states the on-disk size of a built table for each corpus.

**Risks.** `delete_unverified=True` is needed because the files are seconds old; it must never run against a table another process is reading (a server pointed at the same URI during ingest could see a version vanish). `optimize` may also compact fragments, which changes `_rowid`s — harmless here because perf-1's ranking and take happen within one query on a table that is only ever read after ingest completes.

**First step.** One PR: the optimize call, the log line, the double-ingest size test, and a sentence in docs/development/deployment.md.

**Spike.** `ingest_df(db, fixture)` twice into one temp db; `du -s` the table directory and `len(table.list_versions())` after each; then repeat with `table.optimize(cleanup_older_than=timedelta(0), delete_unverified=True)` after each ingest.

## `perf-7` — A corpus-shaped synthetic generator so the 7.8M-row shape is measured nightly rather than asserted

**pending (0/3 verdicts in) · effort XL · impact 4/5**

**What the code does today.** The comment at dataset.py:101-103 says the 10k cap is 'routine for tuomiokirjat (7.8M)'; nothing in the repository ever runs at more than 18 rows in CI (conftest.py:249-254) or 6,876 rows on a maintainer's machine (test_search_invariants.py:215-262). Replicating the fixture shows that scaling is term-dependent: from 54k to 540k rows the ranking-only cost of an every-document term went 12.6 -> 31.1 ms, `fuzzy=1` on 'Åbo' 14.8 -> 65.7 ms, the LIKE place filter 16.1 -> 57.4 ms, a phrase 5.2 -> 15.8 ms, the year-range filter 10.7 -> 22.5 ms, while a capped rare-term ranking stayed ~10 -> 17 ms. The fastest-growing paths are exactly the ones the tool tells the model to reach for: `fuzzy=1` as 'the right second attempt' (df_tool.py:158-164) and the substring filters that are deliberately unindexed (dataset.py:210-212, `text_contains` at :379-386). Replicated text under-represents this: the term dictionary does not grow with copies, so fuzzy's dictionary scan and the LIKE scan are both optimistic. The corpus itself is unreachable from CI (no network to Sisältöhaku) and cannot be committed.

**The gap.** The project's central scaling claim rests on extrapolation from a corpus 1,000x smaller, with the cost curves that matter most (fuzzy, LIKE, common Swedish function words that the stop-word decision keeps searchable) being the ones replication hides.

**The proposal.** `scripts/synth_corpus.py`: fit a shape model on the real df export when present (maintainers have it) and commit only the parameters as `benchmarks/corpus_shape.json` (~1 KB, no text): per-language vocabulary size and Zipf exponent, document-length distribution, 36% empty transcripts, place/language/year marginals, the spelling-variant rate (fit so that 'bref' 257 / 'breff' 1,918 / overlap 71 is reproduced within 20%), and the frequency of 'de'/'den'/'om'. Generate N rows deterministically (seeded) in the JSONL shape `ingest_df` reads, with a tuomiokirjat profile (2.4 KB pages, court-record vocabulary drawn from the same Zipf model). Nightly Dagger `bench-scale` at 1M rows on a standard runner, weekly at 7.8M on a 32 GB self-hosted or large runner: ingest rows/s, index build seconds and peak RSS, bytes per row, and p50/p99 for the perf-3 scenario list plus every-doc terms, fuzzy=1, LIKE, phrase and cold-cache first query. Gates written as product decisions: `fuzzy=1` p99 at 7.8M < 2 s and LIKE filter p99 < 2 s, else the tool description and the filter design must change (e.g. an exact/bitmap `issuingplace` plus a prefix index) before tuomiokirjat is announced. Publish to the same performance history page.

**Why it is once-in-a-lifetime.** It is the only way to prove 'scales to 7.8M pages' without the corpus in CI, and it would make this the reference for how to benchmark an archival search server whose data cannot be shipped — a shape file instead of a dataset. It also stress-tests the project's own corpus-specific decisions (stop words kept, fuzzy as the second attempt, unindexed substring filters) at the scale where they bite.

**How we would know.** The synthetic df at 6,876 rows reproduces five measured corpus numbers within 20% (bref/breff overlap, 'de' 1,735, 'den' 846, 'om' 1,133, 'konung' 279); a weekly run at 7.8M reports ingest rows/s, index build time and peak RSS, and p50/p99 for >= 15 scenarios; a documented go/no-go table for tuomiokirjat with the thresholds above.

**Risks.** A Zipf model does not reproduce real posting-list skew or OCR noise, so absolute numbers are indicative; the fit-validation against df's measured numbers is what keeps it honest. A 7.8M-row weekly run costs machine hours and needs a runner with tens of GB of RAM until perf-4 bounds the index build. The generator must not be mistaken for test data for retrieval quality — it is for cost curves only, and the docs must say so.

**First step.** PR 1: `synth_corpus.py` with the shape file fitted on df and a test that the synthetic df reproduces the five numbers; PR 2: Dagger `bench-scale` at 1M with the perf-3 scenarios; PR 3: the weekly 7.8M run and the go/no-go page.

**Spike.** Fit the shape on the 18-row fixture as a stand-in (vocabulary, doc lengths, empty-transcript rate), generate 540k rows with a seeded Zipf sampler over a 50k-term dictionary, ingest via `ingest_df`, and compare fuzzy=1 and LIKE costs against the x30000 replica: a real dictionary should make fuzzy visibly worse than the 65.7 ms the replica shows.
