# Scale engineering for 7.8M pages

Every proposal from this lens in full, followed by the three skeptics' verdicts on it.
Effort and impact are the lens's own estimates; the verdict tally is the skeptics'.

## `scale-1` — Rank by row id, take only the page: same ranked set, 1/15th of the cost

**survived 3/3, with corrections · effort S · impact 5/5**

**What the code does today.** packages/kansallisarkisto-lib/src/ra_mcp_kansallisarkisto_lib/dataset.py:307-309 projects every column except searchable_text, :315 fast_search(), :326 `query.limit(MAX_TOTAL_COUNT).to_list()` materialises up to 10,000 full rows (transcript included) as Python dicts, :336-337 slices the page in Python and discards the rest. The docstring at :249-254 already names this as the cost (6.1 MB -> 3.3 MB on df) and treats projection as the mitigation. Measured on a 100k-doc synthetic table (300 tokens/doc): a term with >10k hits costs 253 ms p50, +116 MB RSS per call, 19.1 MB read, 62 storage requests, 6,580 iops. The same ranked set as `_rowid`+`_score` only (`select(["_rowid","_score"]).with_row_id(True)`) costs 16.6 ms and the plan has no LanceRead node at all (`ProjectionExec -> GlobalLimitExec fetch=10000 -> MatchQuery`); `table.take_row_ids(page_ids).select(columns)` for 25 rows costs 4.6 ms, 24 requests, 466 KB. Native `.offset()` across separate queries scrambled 684 of 2,000 rows on the same table (dups=missing=684) while a repeated single query is deterministic, so the project's 'one ranked set' argument (:243-247) is correct and must be preserved.

**The gap.** Every search pays for 9,975 rows it throws away. At 7.8M court pages (~2.5 KB each) a common term means ~25 MB of transcript through Arrow->dict per call, ~120 MB RSS per in-flight query, and on object storage 60+ range requests. FastMCP runs sync tools on a threadpool, so 20 concurrent common-term searches is ~2.4 GB of transient memory for 500 rows anyone reads.

**The proposal.** In `lancedb_fts_search`: phase 1 builds the same query but `.select(["_rowid","_score"]).with_row_id(True).fast_search().limit(MAX_TOTAL_COUNT).to_arrow()` — an Arrow table of at most 10,000 (rowid, score) pairs (160 KB). `total = len(ranked)`; `page_ids = ranked["_rowid"][offset:offset+limit]`. Phase 2: `table.take_row_ids(page_ids.to_pylist()).select(columns).to_arrow()`, then re-attach `_score` from phase 1 and restore ranked order (take does not promise order; reorder by a dict rowid->position). Return the page as today. Keep MAX_TOTAL_COUNT, keep `where` on phase 1 (the plan shows ScalarIndexQuery prefilters inside MatchQuery, unchanged). Span attributes gain `db.response.ranked_rows` and `db.response.page_bytes`. Both phases run against the same table handle so row ids are consistent within one version (row ids are addresses; never persist them across versions or expose them).

**Why it is once-in-a-lifetime.** It is the one change that makes 'scales to 7.8M pages without changing shape' literally true: pagination semantics, totals, filters and tests stay identical while per-query cost stops depending on how common the word is. It is also the prerequisite for object storage (proposal scale-5) and for honest totals (scale-2).

**How we would know.** On the 100k synthetic table: common-term p50 253 ms -> ≤25 ms; RSS delta per call 116 MB -> <2 MB; LanceRead `requests` 62 -> ≤25 and `bytes_read` 19 MB -> <0.5 MB (from `analyze_plan`). `test_pages_tile_the_result_set_without_gaps_or_repeats`, `test_repeating_a_query_gives_the_same_order` and `test_paging_past_the_end_keeps_the_total_honest` pass unchanged. Add an invariant: `len(page) == len(ranked[offset:offset+limit])` and scores in the page are non-increasing.

**Risks.** `with_row_id`/`_rowid` is a stable public knob in lancedb 0.38 but row ids are row *addresses* unless stable row ids are enabled at table creation; safe only because both phases use one handle on one version — pin that with a comment and a test that re-ingests between phases is not possible. `take_row_ids` returns rows in address order, so the reorder step is load-bearing. Slight change in the `_score` deprecation path: request `_score` explicitly in phase 1 only.

**First step.** One PR touching `dataset.py` only: split `lancedb_fts_search` into `_rank(table, request, where) -> pa.Table` and `_take(table, row_ids, columns) -> list[dict]`, wire them, and add the two invariants above plus a benchmark-style assertion in `test_search_invariants.py` that the projection of the ranking query contains only `_rowid` and `_score` (`explain_plan()` must not contain `LanceRead` above `GlobalLimitExec`).

**Spike.** cd repo; uv run python - <<'EOF'\nimport lancedb,time\nfrom lancedb.query import MatchQuery,FullTextOperator\nfrom ra_mcp_kansallisarkisto_lib.ingest import ingest_df\nfrom ra_mcp_kansallisarkisto_lib.dataset import FTS_COLUMN,lancedb_fts_search\ndb=lancedb.connect('/tmp/scratch/db'); t=ingest_df(db,'packages/kansallisarkisto-lib/tests/fixtures/df_sample.jsonl')\nq=t.search(MatchQuery('Åbo',column=FTS_COLUMN,operator=FullTextOperator.AND),query_type='fts').select(['_rowid','_score']).with_row_id(True).fast_search().limit(10000)\nprint(q.explain_plan()) # no LanceRead node\nranked=q.to_arrow(); ids=ranked['_rowid'][0:2].to_pylist()\nprint(t.take_row_ids(ids).select(['df']).to_list(), [r['df'] for r in lancedb_fts_search(db,'df','Åbo',limit=2).records])\nEOF\nThen scale it: generate N=100k rows by Zipf-sampling the fixture vocabulary (as done in this audit's scratchpad scale.py) and time `limit(10000).to_list()` vs rowid-only vs take(25) with `analyze_plan()` for `requests=` and `bytes_read=`.

## `scale-2` — Honest totals above 10,000: a counting phase that only runs when the ranked window saturates

**survived 3/3, with corrections · effort M · impact 4/5**

**What the code does today.** dataset.py:32-37 states lancedb has no count API and caps `total_hits` at MAX_TOTAL_COUNT=10_000; :351 sets `total_is_capped`; :461 renders it as `10000+`; the SearchResult comment at :101-103 says capping will be 'routine for tuomiokirjat'. formatter footer at :475-477 stops offering pages at 10,000. Measured: `count_rows("contains_tokens(searchable_text, ...)")` is a full scan without the analyser (1.1-1.2 s at 100k rows; 'abo' -> 0 while 'Åbo' -> 7, 'konungen' -> 0 while MatchQuery finds 3) so it is not a count API either. A `_rowid`-only FTS query with `limit=100_000` returned all 100,000 postings of the commonest term in 83 ms; `limit=1_000_000` in 68 ms (no extra cost when hits < limit).

**The gap.** On 7.8M court pages 'och', 'kyrkia', 'ting' each hit hundreds of thousands to millions of pages; 'sochn' hits tens of thousands. All of them will read `10000+` to the model, which cannot tell a 12,000-hit term from a 3,000,000-hit one — exactly the 'total is a claim about the whole result set' problem the match_all comment (:256-264) was written to avoid.

**The proposal.** After scale-1, `total_hits` comes from the row-id phase. Add `COUNT_CEILING = 1_000_000` and `count_mode: Literal['exact','floor']` to SearchResult. When phase 1 returns exactly MAX_TOTAL_COUNT rows, run a second row-id-only query with `.select(["_rowid"]).limit(COUNT_CEILING)` and report `len()` as exact if < COUNT_CEILING, else floor `1000000+`. Cache that count in a process-wide `functools.lru_cache(maxsize=4096)` keyed on (table version, keyword, where, match_all, fuzzy) so pagination through a saturated query pays it once. Formatter: `showing 25 of 1,234,567 records` / `of 1000000+ records`; the page window stays 10,000 and the footer says so ('pages beyond 10,000 are not offered; narrow with a filter'). Span attribute `db.response.count_mode`. Budget: the count phase costs ~0.8 ms per 1,000 postings measured; set a `COUNT_TIMEOUT_MS=1500` via `to_batches(timeout=...)` and fall back to `floor`.

**Why it is once-in-a-lifetime.** No archival search engine tells a historian both 'how much is there' and 'how far can you page' as two honest numbers. The project already separates them conceptually (total vs page); this makes the separation survive a corpus three orders of magnitude bigger.

**How we would know.** On a 1M-row synthetic table: a term with 250k hits reports `total_hits=250000, count_mode='exact'` in ≤300 ms extra on the first page and 0 ms on subsequent pages; a term with 10,000 < hits < 1M never reads `10000+`. A test pins that a saturated search's second page hits the count cache (span attribute or counter).

**Risks.** Argues against the stated stance that a `10000+` floor is 'honest enough' — it is honest but uninformative at 7.8M. A 1M-row-id fetch is ~8 MB of Arrow and up to ~1 s CPU per distinct saturated query; without the cache a hostile client can make it a DoS vector on the HTTP transport (already listed as an open concern in audit 2 finding 11). At 7.8M pages WAND top-k with k=1M is close to a full posting-list walk; the timeout fallback is what keeps p99 bounded.

**First step.** Implement `count_mode` and the second query behind a keyword-only argument `exact_total: bool = False` in `lancedb_fts_search`, default off; wire `DfSearch.search` to pass it; add the formatter rendering; measure on the synthetic table; flip the default on once the 1M-row benchmark (scale-6) shows p99 ≤ 1.5 s.

**Spike.** Build the 100k synthetic table (scale-1 spike), then time `t.search(MatchQuery(term,...),query_type='fts').select(['_rowid']).fast_search().limit(L).to_arrow()` for L in (10_000, 100_000, 1_000_000) on the rank-1, rank-200 and rank-20000 vocabulary terms; plot ms vs postings. The audit measured 83 ms for 100k postings.
