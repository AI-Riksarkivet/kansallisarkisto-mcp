## `ir-1` — A relevance test collection and regression gate built from simulated known-item topics, variant clusters and facet topics — no historians needed to start

**survived 3/3, with corrections · effort XL · impact 5/5**

**What the code does today.** Retrieval quality is asserted with hand-measured anecdotes written into prose and docstrings: dataset.py:47-59 (bref 257 / breff 1,918 / overlap 71; konungen 279->6), search-tips.md:53-70, data-sources.md:141-147. The only automated quality check is packages/kansallisarkisto-lib/tests/test_retrieval_quality.py:110-128, a binary reachability sweep (does the record appear in the top 100 for any of the first five >6-letter words) — no rank, no MRR, no recall@k, no baseline file. The corpus-only tests at test_search_invariants.py:216-262 pin four numbers (>500, >4x, ==0) with no tolerance model and skip in CI. Nothing measures whether a ranking change (a boost, an analyser, a new query shape) made things better or worse.

**The gap.** Every retrieval decision in this project — stop words kept, fuzzy off, stemming on, concatenated field — was measured once by hand and cannot be re-measured automatically. Proposals ir-2, ir-3, ir-6 and ir-7 all change ranking; without a collection they are four more anecdotes. The corpus has no relevance judgments and no historians on call, but it has three sources of free, defensible labels: (1) known-item topics simulated from each charter's own text (Azzopardi-style), (2) orthographic variant clusters, where the relevant set for 'bref' is every charter containing any variant of the word, (3) the catalogue facets (indexterm x issuingplace x year) which define topical sets ('bishops' charters issued at Åbo 1400-1450') whose members are known exactly.

**The proposal.** New module packages/kansallisarkisto-lib/src/ra_mcp_kansallisarkisto_lib/evaluation.py with: simulate_known_item_topics(table, per_record=3, modes=('rare','common'), lengths=(1,2), seed=7) — samples idf-weighted or df-weighted alphabetic tokens >=4 chars from searchable_text; a 'perturbed' variant applying one scribal perturbation (y<->i, doubled consonant, w<->v, dropped final -e) to model a user who spells differently from the scribe; variant_cluster_qrels(table, clusters) built from ir-3's df_variants table; facet_topics(table) — (indexterm, issuingplace, decade) cells with 5-200 members, query = the Finnish index term word + place; metrics mrr(), success_at(k), recall_at(k), ndcg(k) as plain functions over ranked df lists. scripts/evaluate.py runs a named set of configurations (today-exact, today-fuzzy1, union, norm, fields) over eval/df/topics.jsonl and writes eval/df/report.json; eval/df/baseline.json is committed with the accepted numbers; `make eval`. A corpus-only pytest test_evaluation_gate.py asserts MRR >= baseline-0.02 and recall@100(variants) >= baseline-0.01 and fails on regression; on the 18-row fixture the harness runs end-to-end (as a smoke test of the harness, not of quality) so CI exercises it. Fourth label source once network exists: scripts/harvest.py already speaks to Sisältöhaku's /api/search — record its top-20 for each topic as an external oracle and report rank-biased overlap, so the archive's own Elasticsearch ranking becomes a reference point rather than a competitor.

**Why it is once-in-a-lifetime.** It turns 'measured once by the author' into 'measured on every commit', which is the difference between a well-argued search engine and a proven one. It is also what lets the next corpus (voudintilit, tuomiokirjat) be a week's work: run the harness, read the report, decide. No archival MCP server has a committed baseline.json for ranking quality; this would be the reference for how to build one without a judged collection.

**How we would know.** eval/df/report.json exists and is regenerated by `make eval` in under 60 s on the full df table; every ranking-affecting PR must show the before/after table. Spike numbers become the first baseline: on 204 simulated topics over the fixture, exact AND MRR=0.829 / success@10=1.00; fuzzy=1 MRR=0.529 (the stemming loss, now a number); perturbed-query MRR for exact AND = 0.034 (the orthography problem, now a number). On the corpus, the gate holds konung/ecclesia/Åbo counts and MRR within tolerance.

**Risks.** Simulated known-item topics measure findability, not topical relevance; they reward exact-term systems and must be read alongside the variant-cluster and facet metrics, or the harness will 'prove' that fuzzy is always worse. Facet topics inherit the catalogue's incompleteness (2,314 charters have no place). The corpus-only gate runs only where .data/df exists, i.e. on a maintainer's machine, unless the harvested export is cached in CI — which the project has chosen not to do. Argues against nothing the project states; it fulfils 'every decision measured' by making the measurement repeatable.

**First step.** Add evaluation.py with simulate_known_item_topics(), mrr(), success_at() and scripts/evaluate.py that runs two configurations (exact AND, fuzzy=1) and prints MRR/success@1/success@10 for verbatim and perturbed topics; commit eval/df/baseline.json produced against the fixture so CI can diff it. ~250 lines, the spike script is 80% of it.

**Spike.** Already run: /tmp/claude-0/-home-user-kansallisarkisto-mcp/6ff06e2b-109d-555b-be3f-fc58e4c2ea7f/scratchpad/ir/exp_f.py generates 204 topics from the 18-row fixture and evaluates three configurations: exact AND (MRR 0.829 verbatim, 0.034 perturbed), fuzzy=1 (0.529 / 0.349), per-term stem|fuzzy union (0.817 / 0.418). ## `ir-2` — Dissolve the stemming-vs-fuzzy exclusivity with a per-term BooleanQuery(SHOULD stemmed, SHOULD fuzzy) — fuzzy=1 stops costing stemming

**survived 3/3, with corrections · effort S · impact 5/5**

**What the code does today.** dataset.py:44-60 states that 'the engine makes fuzzy matching and stemming mutually exclusive' and builds DEFAULT_FUZZINESS=0 on it; dataset.py:304-305 sends the whole keyword as one MatchQuery(keyword, operator, fuzziness=fuzzy). search-tips.md:59-70 and data-sources.md:145-147 repeat the exclusivity as a property of the engine ('konungen with fuzzy=1 collapses from 279 to 6'). test_search_invariants.py:29 (BASE_TERMS) and :102 (test_fuzzy_widens_a_base_form) restrict the 'fuzzy widens' invariant to base forms precisely because it is false for inflected ones. The tool description at df_tool.py:157-165 teaches the model a workaround ('pass a base form').

**The gap.** The exclusivity is a property of a single MatchQuery, not of the engine. lancedb 0.38 exposes BooleanQuery with Occur.SHOULD/MUST (verified: lancedb.query.BooleanQuery, Occur). Measured on the fixture: BooleanQuery([(SHOULD, MatchQuery(t)), (SHOULD, MatchQuery(t, fuzziness=1))]) returned exactly exact ∪ fuzzy for 8 of 8 terms — konungen 3/0/3, konung 3/5/5, biskop 1/3/3, Abo 7/8/8 — and MUST-of-per-term-SHOULD-groups gives match_all semantics; it composes with .where() and .fast_search(). On the known-item harness the union scores MRR 0.817 verbatim (fuzzy=1 today: 0.529) and 0.418 on perturbed queries (fuzzy=1 today: 0.349): it dominates today's fuzzy on both axes and matches exact on verbatim.

**The proposal.** In dataset.py replace lines 304-305 with a _build_query(keyword, match_all, fuzzy) helper: split on whitespace; for each term build MatchQuery(term, column=FTS_COLUMN, boost=2.0) and, when fuzzy>0 and len(term)>=4, add MatchQuery(term, column=FTS_COLUMN, fuzziness=fuzzy, prefix_length=1); wrap the pair in BooleanQuery([(SHOULD, exact), (SHOULD, fuzzy)]); combine terms with Occur.MUST when match_all else Occur.SHOULD. Two guard rails come from measurement: boost=2.0 on the exact clause because summed scores otherwise let a fuzzy-only hit outrank stemmed ones (for 'Abo', DF 1 rose to #1 via 'bo', a Swedish content word one deletion away); the 4-character floor because fuzzy on Latin function words is pure noise on the fixture ('de' 9->18 of 18 docs, 'om' 3->11, 'et' 5->15). Then: rewrite dataset.py:44-60, search-tips.md:59-70, data-sources.md:145-147 and the df_tool.py:157-165 field text ('fuzzy=1 now keeps stemming; short words are never fuzzed'); widen test_fuzzy_widens_a_base_form to every term (drop BASE_TERMS restriction) as the new invariant 'fuzzy never narrows'; remeasure bref (2,212 + stemmed forms) and konungen (>=279) on the corpus and pin them in the corpus-only tests.

**Why it is once-in-a-lifetime.** It removes the single largest documented limitation of the search with ~40 lines, and converts a paragraph of warnings the model has to obey into a property the engine guarantees. Once fuzzy no longer sacrifices stemming, the question 'should fuzzy be the default?' becomes an empirical one the harness can answer, instead of a settled no.

**How we would know.** search('konungen', fuzzy=1).total_hits >= search('konungen').total_hits on the corpus (today 6 vs 279); the 'fuzzy widens' property holds for all terms in a randomly sampled 500-token vocabulary; harness MRR for fuzzy=1 rises from 0.53 to >=0.80 verbatim with perturbed MRR not lower than today's 0.35; bref with fuzzy=1 still >= 2,212.

**Risks.** Scores are summed across clauses, so _score changes meaning and any ranking documented as 'BM25' is now BM25 over a disjunction; documented counts for fuzzy queries change and must be remeasured. BooleanQuery cannot carry a quoted phrase, so the existing quoted-phrase rejection stays. A model that passes fuzzy=2 still gets the 67%-precision behaviour the docs warn of; consider clamping the tool field to le=1. Argues directly against the stated design reasoning in dataset.py:44-60 — the reasoning was right about MatchQuery and wrong about the engine.

**First step.** Add _build_query() to dataset.py and route the non-quoted branch through it; move test_fuzzy_widens_a_base_form to a parametrisation over every alphabetic token >=4 chars in the fixture vocabulary; update the four prose sites. One PR, ~120 lines including tests.

**Spike.** Already run: scratchpad/ir/exp_a.py (union == exact ∪ fuzzy on 8/8 fixture terms, AND via MUST groups, where+fast_search compose) and scratchpad/ir/exp_h.py (ranking order under summed scores; fuzzy noise on 2-letter words; prefix_length effect). Both finish in <10 s on the fixture.
