## `ops-1` — Make the RED histograms able to answer a latency SLI, and count the error strings the spans hide

**survived 3/3, with corrections · effort S · impact 4/5**

**What the code does today.** dataset.py:83 declares `kansallisarkisto.lancedb.query.duration` with unit "s" and dataset.py:87 `kansallisarkisto.lancedb.results`; telemetry.py:86 builds `MeterProvider(resource=..., metric_readers=[...])` with no `views`, so the SDK default explicit buckets (0, 5, 10, 25, 50, 75, 100, 250, 500, 750, 1000, 2500, 5000, 7500, 10000) apply. Those boundaries are sized for milliseconds; the instrument records seconds. Verified with an InMemoryMetricReader (scratchpad/ops/spike_buckets.py): the ten latencies measured on the capacity spike (10 ms .. 7.8 s) land 8 in the [0,5] bucket and 2 in [5,10] — no p50/p95/p99 is recoverable from the exported histogram. Separately, the counted failures are only exceptions: dataset.py:82/330 increments `.errors` inside `except Exception`; the text-returned failures — `require_keyword`/`require_ordered_range` at df_tool.py:175/178, `MissingTableError` and `SearchInputError` in `_answer` at df_tool.py:31-56 — are marked on the span by `mark_span_error` (lib/telemetry.py:79-97) but reach no metric. An availability SLI therefore cannot be computed from metrics, only from (sampled) spans.

**The gap.** The project's own claim (dataset.py:76-78: 'an error-rate panel and a latency percentile both work') is false for latency under the SDK it ships with, and half-true for errors: the class of failure this server was designed around (returning text) is invisible to metrics.

**The proposal.** In `init_telemetry()` pass `views=[View(instrument_name="kansallisarkisto.lancedb.query.duration", aggregation=ExplicitBucketHistogramAggregation((0.005,0.01,0.025,0.05,0.1,0.25,0.5,1,2.5,5,10))), View(instrument_name="kansallisarkisto_mcp.tool.duration", aggregation=<same>)]` to the `MeterProvider` at telemetry.py:86, and pin the boundaries as a module constant `LATENCY_BUCKETS_SECONDS` next to `SHUTDOWN_TIMEOUT_SECONDS` with the measured reasoning. Add in df_tool.py a meter `kansallisarkisto_mcp` with `tool.calls` counter (attributes `tool`, `outcome` in {ok, empty, validation, missing_table, timeout, internal}) and `tool.duration` histogram (unit s, attribute `tool`), recorded once per call from `_answer` (wrap `produce()` in perf_counter; `empty` when the formatted text starts with 'No ' so the behavioural signal survives), and from the two early-return branches at df_tool.py:174-179. Keep `.results` as is — its default 0-bucket is exactly the 'matched nothing' count the comment at dataset.py:84-87 wants. Test in test_telemetry.py with `InMemoryMetricReader`: a 0.35 s record lands in bucket index 6 (0.25–0.5), a blank keyword increments `tool.calls{outcome=validation}`, a missing table increments `outcome=missing_table`.

**Why it is once-in-a-lifetime.** It turns the existing instrumentation from decorative into the two SLIs every later proposal (SLOs, alerts, HPA, the load-test gate) is computed from — and it is the kind of measured, written-down correction the codebase is built on: 'the buckets were in the wrong unit, here is the bucket table and why'.

**How we would know.** Exported histogram for a fixture search has ≥3 non-empty buckets across a 10 ms..8 s sample set (today: 2, both useless); `sum(rate(tool_calls{outcome=~"internal|timeout|missing_table"}))/sum(rate(tool_calls))` is computable from metrics alone and equals the span-derived error rate on the smoke test within 0.

**Risks.** A View with explicit buckets is SDK-only and stays in the server package, so the lib's API-only rule (lib pyproject: 'API only, never the SDK') holds. `outcome=empty` from a string prefix is brittle; better to thread a SearchResult flag, which touches `_answer`'s Callable signature.

**First step.** One PR: the two Views in telemetry.py, the `tool.calls`/`tool.duration` instruments in df_tool.py, the three InMemoryMetricReader tests, and a sentence in observability.md replacing 'a latency percentile works' with the bucket table.

**Spike.** cd repo && /tmp/uvenv/bin/uv run python <scratchpad>/ops/spike_buckets.py — prints the default bucket counts [0,8,2,0,...] versus the seconds-scaled View's spread across 8 buckets for the same ten observations.

## `ops-3` — 'Degraded' as a first-class state: a query deadline, an in-flight gate, and a readiness body that carries table identity and evicts a dead connection

**survived 3/3, with corrections · effort L · impact 5/5**

**What the code does today.** dataset.py:326 runs `query.limit(MAX_TOTAL_COUNT).to_list()` with no deadline; lancedb 0.38's `to_list(*, timeout: timedelta | None)` exists and is honoured — measured on a 40k-page synthetic table: a 260 ms capped query given `timeout=50ms` returns `RuntimeError: lance error: Query Execution error: Execution error: Query timeout after 50 ms` in 55 ms (scratchpad/ops/spike_timeout.py). Tools are sync and run on anyio's worker pool (df_tool.py:6-10), whose default limiter is 40 tokens (measured). Each capped search on ~2.5 KB pages costs +60–100 MB RSS and ~350–690 ms alone; 16 concurrent → p50 6.6 s, wall 7.8 s, RSS 822→1750 MB (spike_concurrency.py). `readiness()` at tools.py:96-111 only calls `get_search()` (tools.py:78-93), which lists table names; `get_lancedb` caches a connection per URI for the process lifetime with no eviction (dataset.py:89-122). Observed on the fixture (spike_failures.py / spike_remount.py): after the table directory is moved away and back, the cached connection recovered in one run and kept answering `Table 'df' was not found` in another depending on which call came first — recovery is not deterministic; evicting `_connections[uri]` recovered deterministically. Also measured: `PROBE_KEYWORD = "probe"` (server.py:21) costs 10 ms because it matches nothing, while a probe on a common term costs 218 ms on 40k rows because a hit materialises 10k rows — the probe term choice is load-bearing and undocumented.
