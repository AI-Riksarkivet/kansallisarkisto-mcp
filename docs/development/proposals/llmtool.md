# LLM tool design and MCP ergonomics

Every proposal from this lens in full, followed by the three skeptics' verdicts on it.
Effort and impact are the lens's own estimates; the verdict tally is the skeptics'.

## `llmtool-1` — A historian-question evaluation harness that scores tool-call trajectories, not just hits

**survived 3/3, with corrections · effort XL · impact 5/5**

**What the code does today.** The only model-facing checks are string assertions on single calls: packages/kansallisarkisto-mcp/tests/test_tools.py:31-35 checks a header appears, scripts/mcp_smoke.py:36-51 runs six fixed calls. Nothing anywhere runs a model over the server and measures what it does with the ~2,700 tokens of guidance in df_tool.py:64-169 and tools.py:19-68. The guidance itself is a list of predicted model mistakes (Turku for Åbo, venäjä, Reval, writing OR at df_tool.py:80-83, fuzzy on an inflected form at df_tool.py:158-164) with no evidence a model makes them or that the prose prevents them. The one hallucination-relevant signal exists only as a span attribute: search_operations.py:132-134 records df.found=False on get_charter misses 'when models cite DF numbers that do not exist', but nothing aggregates it.

**The gap.** Retrieval quality is proven (test_retrieval_quality.py), tool-use quality is asserted. There is no number for: how often a model reaches the right charter, how many calls it wastes, how often it passes a filter value the description explicitly warns against, and how often the DF number it cites never appeared in any tool result. Without that, every description edit is a guess, and the project's stated bar ('a historian trusts and cites it') has no measurement.

**The proposal.** Add evals/ (not shipped in the wheel): (1) evals/questions.yaml with 40-60 historian-style questions written against the corpus, each with gold DF numbers and the trap it exercises, e.g. {q: 'Which charters did the bishop of Turku issue in the 1350s?', gold: [670, ...], traps: [modern_place, index_term]}, {q: 'Find letters mentioning Reval around 1380', gold: [891], traps: [modern_vs_historical_place]}, {q: 'Quote the opening of DF 1215', gold: [1215], traps: [quotation_fidelity]}. Fixture-only questions are marked so the harness runs offline on the 18 rows. (2) evals/run.py: for each question, open an in-memory fastmcp.Client(tools.kansallisarkisto_mcp), convert list_tools() to Anthropic tool definitions, drive a manual tool-use loop with the anthropic SDK (model claude-opus-5, thinking {type: adaptive}, max 8 tool calls, strict tool schemas), and write one JSONL trajectory per question: every tool_use input, every tool result text, the final answer, token usage. (3) evals/score.py, pure Python, no network: found@answer (gold DF present in final answer), first-hit call index, wasted calls (calls after the gold was already in a result, plus calls returning 'No ... results'), wrong-filter rate (issuingplace/language values matched against a deny-list derived from the descriptions: Turku, Viipuri, Reval, Danzig, Dorpat, venäjä; keyword containing bare AND/OR/NOT; fuzzy>0 with a quoted phrase), hallucinated-DF rate (any 'DF \d+' in the final answer whose number never appeared in a tool result of that trajectory), URL correctness (every df.kansallisarkisto.fi/document/N in the answer has N in a result), quotation fidelity (any quoted span of >=8 words must be a substring of a returned transcript after whitespace normalisation), and tokens per resolved question. (4) A pytest test that runs score.py over a checked-in golden trajectory so the scorer itself is tested offline; the live run is a Make target (make eval) gated on ANTHROPIC_API_KEY, never CI. Report as evals/REPORT.md with one row per metric, and commit the report alongside any change to a description string.

**Why it is once-in-a-lifetime.** No archival MCP server publishes a measured tool-use score. This turns the project's most distinctive asset, its long measured descriptions, from prose into a tested artefact: every sentence either moves a metric or is deleted. It also gives the sibling ra-mcp and ape-mcp a harness they can reuse verbatim, since the scorer only needs tool names and DF-style identifiers. And hallucinated-DF rate is exactly the number a historian would ask for before trusting the tool.

**How we would know.** A committed evals/REPORT.md with, for one model at one date: found@answer >= 0.85 on the corpus set; hallucinated-DF rate = 0.00 (any nonzero is a bug in either the description or the formatter); wrong-filter rate < 0.05; mean wasted calls < 0.5; median tokens per resolved question. Every subsequent description change must show the delta.

**Risks.** Costs real money per run (about 50 questions x 4 calls x ~6k tokens ≈ $6-10 per model at Opus 5 rates) and needs the full corpus, which cannot be harvested in this environment; gold answers need a historian's hour to write honestly. Scores are model- and date-specific and will drift; the scorer must not be over-fitted to one model's phrasing. Argues mildly against the project's 'stdio must cost nothing' stance only in that evals/ adds an optional dependency on the anthropic SDK; keep it out of both packages.

**First step.** Land evals/score.py and evals/questions.yaml with the 6-8 fixture-answerable questions (DF 1031 Raseborg 1444, DF 891 Tallinn, DF 404 footnote-fused word, DF 18 contentless charter, a 'Turku' question whose gold is Åbo), plus a hand-written golden trajectory JSONL and a pytest that scores it, asserting hallucinated-DF detection fires on a planted 'DF 9999'. No API key needed for this PR.

**Spike.** Build a trajectory replayer on the fixture: drive tools.kansallisarkisto_mcp through fastmcp.Client with a scripted sequence (df_search Turku -> 0 hits; df_search Åbo -> hits; df_get_charter 1031) and a synthetic final answer containing 'DF 1031' and 'DF 9999'; implement the hallucinated-DF and wrong-filter checks and confirm they flag 9999 and Turku. The in-memory client pattern is proven in scratchpad/spikes/protocol.py; the scorer needs no network.

## `llmtool-2` — Return structuredContent and an outputSchema beside the text, and set isError on error replies

**survived 3/3, with corrections · effort M · impact 4/5**

**What the code does today.** Every tool returns a bare str: df_tool.py:170 and :215 declare -> str, and _answer at df_tool.py:31-56 turns every failure into text with is_error never set. The comment at df_tool.py:171-173 admits the consequence: 'Every return below is a string, not an exception ... which leaves FastMCP's tools/call span green on failure', and mark_span_error exists as a workaround. The formatter's _oneline at formatter.py:20-34 exists solely because the model must parse structure out of text and a field could forge it. Tool annotations at df_tool.py:63 set readOnlyHint and openWorldHint but not idempotentHint, although both tools are idempotent. Spike scratchpad/spikes/protocol.py confirmed on FastMCP 3.4.4 that ToolResult(content=text, structured_content=dict) reaches the client with both halves, that an explicit output_schema is advertised in tools/list, and that ToolResult(is_error=True) delivers the same actionable text with isError=true.

**The gap.** A model reading 25 hits has to re-extract DF numbers, years and URLs from markdown, which is where citation errors come from; a client cannot render hits, cannot build a 'open charter' link, and cannot distinguish an error reply from a result without regex on 'Error:'. The MCP spec has had structuredContent, outputSchema and isError since 2025-06 precisely for this, and the project uses none of them.

**The proposal.** In df_tool.py return fastmcp.tools.tool.ToolResult from both tools. Define in formatter.py two pydantic models: Hit {df: str, df_number: int|None, dating: {start: int|None, end: int|None, rendered: str}, place: str|None, country: str|None, language: str|None, indexterm: str|None, transcribed: bool, score: float, url: str} and SearchPage {total_hits: int, total_is_capped: bool, offset: int, limit: int, next_offset: int|None, hits: list[Hit]}; pass output_schema=SearchPage.model_json_schema() to @mcp.tool. The text block stays exactly as today (older clients and the model's reading order are unchanged). For df_get_charter, structured_content = Charter {df, dating, place, country, language, indexterm, lat, lng, transcript, url, transcribed}. In _answer, wrap the three error branches in ToolResult(content=msg, is_error=True) so FastMCP marks the call failed; keep the text identical so the model's behaviour does not change. Add idempotentHint: True to both annotations. Adjust test_tools.py to assert result.structured_content['hits'][0]['df'] == '1031' and result.is_error on the blank-keyword case; extend mcp_smoke.py with a structuredContent check so the Dagger test-mcp proves the transport carries it.

**Why it is once-in-a-lifetime.** It makes the DF number a typed field rather than a bold prefix the model must copy correctly, which is the single most citation-relevant change available. It also resolves the tension the code comments already name: errors become honest at the protocol level (isError) while remaining text the model can act on, so the 'never raise' philosophy is preserved and the span/failure-rate workaround becomes unnecessary.

**How we would know.** tools/list advertises outputSchema for both tools; every tools/call result carries structuredContent validating against it (test with jsonschema in test_tools.py); error replies carry isError=true and identical text; eval harness (llmtool-1) hallucinated-DF and URL-correctness metrics are computed from structuredContent rather than regex; mark_span_error calls in df_tool.py can be removed once FastMCP's own span reflects isError.

**Risks.** structuredContent roughly doubles the bytes per page on the wire (the hit list is serialised twice); measured on the fixture a 25-hit page is ~9.6 kB of text, so the JSON adds ~4-5 kB, but most clients do not feed structuredContent to the model, so the model's token cost is unchanged. Whether a given client shows structuredContent to the model is client-specific; the text block must remain complete. Argues against the stated 'tools return text, never raise' only in form, not substance.

**First step.** PR: add idempotentHint, wrap _answer's three error branches in ToolResult(is_error=True), and assert is_error in test_tools.py for the blank keyword, inverted range and missing-table cases. Structured content follows in a second PR.

**Spike.** scratchpad/spikes/protocol.py already demonstrates all four mechanisms against the ingested fixture through an in-memory Client; extend it by validating structured_content against output_schema with jsonschema (available via pip) to fix the schema shape before touching df_tool.py.
