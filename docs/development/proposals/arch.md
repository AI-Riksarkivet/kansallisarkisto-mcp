## `arch-1` — A corpus is a declarative CorpusSpec; ingest, search, indexes, tool signatures and the invariant suite are derived from it

**survived 3/3, with corrections · effort XL · impact 5/5**

**What the code does today.** The 'spine' is shared but every corpus fact is hand-threaded through six files. dataset.py:416-419 says 'Every corpus tool wraps lancedb_fts_search in the same shape ... Only the label and the per-record rendering differ', yet that shape is not a type anywhere. search_operations.py:97-103 maps five filters to predicates by hand (equals/text_contains/at_least/at_most); ingest.py:147-152 lists the index plan by hand (btree=df_number,year_from,year_to; bitmap=language,issuingplacecountry); test_search_invariants.py:59-66 re-lists the same plan a third time; ingest.py:30-48 hand-types DF_SCHEMA field by field even though it is a 1:1 image of DfRecord (models.py:56-89) plus searchable_text; df_tool.py:87-170 declares the same five filters a fourth time as Annotated parameters; config.py:25-28 says 'voudintilit and tuomiokirjat get their names here when they get an ingest'. Adding a corpus today means touching models.py, ingest.py, config.py, search_operations.py, a new *_tool.py, formatter.py, tools.py, server.py:40, errors.py, and three test files. Spike B proved schema_from_model(DfRecord, {'searchable_text': string}).equals(DF_SCHEMA) is True; spike C proved FastMCP 3.4.4 honours a synthesised inspect.Signature (client saw ['keyword','offset','limit','language','issuingplace','year_min','year_max'] with correct anyOf/int-or-null JSON schema and dispatched the call).

**The gap.** The next corpus is not 'a week's work'; it is a re-implementation of df with different nouns, and every one of the four copies of the filter list can drift independently (the index plan and the predicate builder already live 200 lines apart in different modules, coupled only by convention).

**The proposal.** New module packages/kansallisarkisto-lib/src/ra_mcp_kansallisarkisto_lib/corpus.py: @dataclass(frozen=True) class FilterSpec: name: str; column: str; kind: Literal['equals','contains','at_least','at_most']; py: type[str]|type[int]; description: str; example: str|int. Method predicate(value) -> str dispatches to the existing equals/text_contains/at_least/at_most; property index -> 'Bitmap' for equals, 'BTree' for at_least/at_most, None for contains (this is exactly the reasoning in dataset.py:203-213, made executable). @dataclass(frozen=True) class CorpusSpec: name ('df'); table ('df'); record: type[BaseModel] (DfRecord); id_field ('df'); id_column_int ('df_number'); label ('Diplomatarium Fennicum'); noun ('charter'); fts_language ('Swedish'); filters: tuple[FilterSpec,...]; range_pairs: tuple[tuple[str,str],...] (('year_min','year_max'),) for require_ordered_range; example_keyword ("'konung' or 'littera'"); url_template ('https://df.kansallisarkisto.fi/document/{id}'); render_record: Callable; render_full: Callable; fixture: Path; description_template: str; instructions_template: str. Derived methods: schema() (spike B's 12-line function), index_plan() -> {column: 'BTree'|'Bitmap'} from filters plus id_column_int, where(**values) -> combine(...), searchable_columns(). corpora/df.py holds the one instance (the prose from df_tool.py moves here as templates, see arch-2). ingest.py becomes ingest(db, spec, jsonl) using spec.record.from_json, spec.schema(), build_fts_index(language=spec.fts_language), build_scalar_indexes(**spec.index_plan()). search_operations.py becomes CorpusSearch(db, spec) with search(keyword, *, limit, offset, match_all, fuzzy, **filters) validating filter names against spec and get(id). MCP side: corpus_tools.py register_corpus(mcp, spec, get_search) synthesises '<name>_search' and '<name>_get_<noun>' via the __signature__ technique from spike C, with Annotated[..., Field(description=..., ge/le)] built from FilterSpec; DEFAULT_LIMIT/MAX_LIMIT stay global. tools.py becomes: for spec in CORPORA: register_corpus(...). server.py:40 and readiness iterate CORPORA. Tests: conftest gets a params=CORPORA fixture (see arch-8).

**Why it is once-in-a-lifetime.** It turns the project's own claim ('one implementation instead of each growing its own copy of the same bugs', dataset.py:5-6) from a hope about the spine into a property of the whole stack: the second corpus costs one ~150-line spec file plus a fixture, and the third costs the same. Nobody has published an archival MCP server where the corpus is data and the server is a function of it.

**How we would know.** voudintilit lands as packages/kansallisarkisto-lib/src/ra_mcp_kansallisarkisto_lib/corpora/voudintilit.py (<= 200 lines incl. prose) + tests/fixtures/voudintilit_sample.jsonl and nothing else changes outside CORPORA; `grep -rn 'year_from\|issuingplacecountry' packages/*/src` returns hits only in corpora/df.py; tools/list shows four tools; the full existing suite passes for df unchanged (194 pass) and the parametrised invariants run for both corpora.

**Risks.** Generated signatures are less greppable than df_tool.py's literal parameters, and an IDE cannot jump to them; mitigate by snapshotting tools/list JSON schema into tests/snapshots/df_tools.json and asserting equality, so any drift is a visible diff. Argues partly against the project's 'prose is load-bearing' philosophy: the descriptions must stay hand-written templates in the spec (never synthesised from field names), only their numbers and parameter lists are generated. Two-corpus abstraction risk: FilterSpec kinds must be extended (e.g. 'in' for voudintilit collections) rather than bent; keep the enum closed and add kinds deliberately.

**First step.** PR 1 (no behaviour change): add corpus.py with FilterSpec/CorpusSpec and corpora/df.py; make ingest_df, DfSearch.search and build_scalar_indexes read the filter list and index plan from DF spec instead of literals; add test asserting DF.schema().equals(DF_SCHEMA) and DF.index_plan() == {'df_number':'BTree','year_from':'BTree','year_to':'BTree','language':'Bitmap','issuingplacecountry':'Bitmap'}; delete the literal list from test_search_invariants.py:59-66 in favour of the spec.

**Spike.** Already run: scratchpad/spike/b_schema_from_model.py (derived schema equals DF_SCHEMA: True) and scratchpad/spike/c_generated_tool.py (FastMCP 3.4.4 accepts a synthesised __signature__ from a FilterSpec list; client JSON schema and dispatch correct). ## `arch-2` — Corpus facts are computed at ingest into a sibling `<table>__facts` table, interpolated into tool descriptions at boot, and every number in prose is checked against them

**survived 3/3, with corrections · effort L · impact 5/5**

**What the code does today.** Numbers that are claims to the model are typed by hand and duplicated: tools.py:19-68 (instructions) and df_tool.py:64-169 carry '6,876', '36%', '815' (Åbo), '687', '311', '499 values', '3,045'/'1,638'/'1,232'/'89', '2,314 (34%)', '833', '28 compound labels'; search-tips.md:88 says 27 compound labels where df_tool.py:115 says 28 (audit finding 9); the id range '1 to 6888' is typed in df_tool.py:214, formatter.py:89 and docs/tools/df-get-charter.md:14,43. A scan (scratchpad spike F) found 139 distinct numeric literals across packages/ and docs/, 87 of them in more than one file, '6876' in 20 files, 76 in non-test source. All of these are import-time string constants, so a server whose mounted table is the 18-row fixture (as in `dagger call test-mcp`, testmcp.go:9-15) or a re-harvest with 7,000 rows tells the model '6,876 charters' regardless. Spike A proved the mechanism: on the fixture, count_rows(filter) + a one-column projection with pyarrow value_counts computed 14 facts in 0.03 s, stored them in a one-row lancedb table 'df__facts' (works for s3:// URIs where a sidecar JSON file would not), and read them back identically.

**The gap.** The project's best property (measured numbers beside the code) is also its rot vector: the numbers cannot be checked, drift has already happened (27/28, 16/18 in the first audit), and the MCP layer cannot say what is actually mounted.

**The proposal.** packages/kansallisarkisto-lib/src/ra_mcp_kansallisarkisto_lib/facts.py: FactSpec = ('rows', count_rows) | ('untranscribed', "transcript = ''") | ('no_place', ...) | value_counts('language') | value_counts('issuingplace', top=12) | vocabulary_size('issuingplace') | min_max('df_number') | min_max('year_from','year_to') | reachable (the sweep from test_retrieval_quality.py:110-128 run over every row: distinctive word -> hit). Each CorpusSpec (arch-1) declares its facts list; compute_facts(table, spec) -> dict; ingest() writes them to '<table>__facts' (schema: table string, facts string(JSON), computed_at string, source_sha256 string, rows int). load_facts(db, table) -> Facts|None. The MCP layer builds descriptions with str.format_map over a Facts view that renders '{rows:,}' and '{untranscribed_pct}%' and '{place.Åbo:,}'; descriptions are rendered when get_search() first builds the facade — so tools/list reflects the mounted table — and fall back to a committed snapshot packages/kansallisarkisto-lib/src/ra_mcp_kansallisarkisto_lib/corpora/facts/df.json (regenerated by `make facts` from the full corpus, reviewed as a diff) when no table is mounted. Docs: scripts/render_facts.py emits docs/how-it-works/_facts/df.md snippets that search-tips.md and data-sources.md include via zensical snippets, so '815' is written once. Guard: tests/test_prose_facts.py loads the snapshot and asserts (a) every {placeholder} in every template resolves, (b) a ruff-style lint over description/instructions strings fails on any bare numeral >= 20 not produced by a placeholder (allow-list for years like 859/1530 that are themselves facts min_max), (c) the docs snippets are current (render to a temp dir and diff).

**Why it is once-in-a-lifetime.** Descriptions become honest per deployment ('serving 18 charters' on the fixture, '7,012' after a re-harvest) and the corpus reference pages become regenerated measurements. No archival MCP server today can tell a model the true size and coverage of the table it is actually searching; this one would, from a mechanism a contributor can read in one file.

**How we would know.** `make facts` on the full corpus followed by `git diff --stat` is empty when nothing changed; tools/list against the fixture table says 'showing ... of 18' in its description and the 27-vs-28 class of drift cannot recur because the number is one placeholder. Count of bare numerals in df description/instructions strings goes from ~60 to 0.

**Risks.** Per-deployment descriptions mean tools/list is not constant across servers, which some MCP client caches assume; keep the tool NAME and parameter schema constant and vary only prose. Computing 'reachable' on tuomiokirjat (7.8M sweeps) is hours: make it an opt-in fact (`--facts full`) and record 'reachable: null' otherwise. This argues against the philosophy of writing numbers next to the code: the resolution is that rationale numbers in comments (e.g. dataset.py:48-52's bref/breff) stay as dated snapshots with a 'measured 2026-07' tag, while numbers in strings the model reads must come from facts.

**First step.** PR: facts.py with compute_facts/store/load for the seven cheapest facts (rows, untranscribed, no_language, no_place, no_year, id min/max, year min/max), written by ingest_df; df_tool.py:214 and formatter.py:89 read the id range from facts instead of '6888'; one test ingests the fixture and asserts facts == {'rows': 18, 'untranscribed': 3, 'no_place': 6, 'no_year': 2, 'df_number_max': 6868, ...} (values from spike A).

**Spike.** Already run: scratchpad/spike/a_stats_table.py — on the 18-row fixture, 14 facts computed in 0.03 s, stored in df__facts and round-tripped equal (untranscribed 3/18 = 17%, id range 1-6868, years 882-1445). Follow-up spike: time compute_facts on a synthetic 1M-row table (duplicate the fixture) to bound the ingest-time cost before tuomiokirjat.
