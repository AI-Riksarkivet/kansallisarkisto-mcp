## `repro-1` — Dataset identity: a snapshot manifest born at harvest, carried in the LanceDB schema metadata, surfaced in /ready, in every tool reply and as an MCP resource

**survived 3/3, with corrections · effort L · impact 5/5**

**What the code does today.** scripts/harvest.py:321-333 writes report.json with index, mode, complete, index_total, documents_written, documents_unreachable, coverage_pct, http_requests, elapsed_seconds, shortfalls — but no harvest timestamp, no base URL, no harvester version/git sha, no hash of the file it just wrote. ingest.py:144 `db.create_table(table_name, data=reader, schema=DF_SCHEMA, mode="overwrite")` carries no metadata at all (spike: `table.schema.metadata` is None after ingest_df). scripts/ingest_df.py:29 reads `.data/df/df.jsonl.gz` and never looks at the report.json harvest.py wrote next to it. tools.py:96-111 readiness() returns `(True, "df")` — a table name, not an identity; routes.py:55 serializes exactly that. formatter.py and dataset.py:446-478 format_results() render the page with no snapshot line. docs/how-it-works/data-sources.md:68-71 states the problem in prose ('Nothing in a harvested file signals that drift') and leaves it there. Spike (scratchpad/spike/determinism.py): `DF_SCHEMA.with_metadata({...})` passed to create_table survives create_table AND all six create_index(replace=True) calls (dataset.py:190,220,222) unchanged; `table.tags.create('harvest-2026-07', version)` works on lancedb 0.38.0.

**The gap.** A running server cannot say which harvest it serves. A historian citing 'DF 2457 via kansallisarkisto-mcp' cannot say when the snapshot was taken or whether it covered 100% or 98.25%; an operator with two /data directories cannot tell them apart; a bug report cannot name the data. The comments say 'the live service is always the authority' but nothing gives the reader the date on which this copy stopped being it.

**The proposal.** 1. `harvest.py`: extend the report into a manifest `<index>/manifest.json` with `harvested_at` (UTC ISO 8601), `base_url`, `harvester` {`git_sha`, `script_sha256` of harvest.py}, `file_sha256` + `file_bytes` of the .jsonl.gz, `record_count`, `content_digest` (repro-2), `source_fields` (sorted union of JSON keys seen — the source schema fingerprint), and the existing coverage fields. Keep report.json as an alias for one release. 2. `ingest.py`: new `read_manifest(jsonl_path)` (sibling manifest.json, optional), and `ingest_df(..., manifest=...)` merges `{ingested_at, lib_version, lancedb_version, pyarrow_version, schema_version: sha256(DF_SCHEMA.serialize()), fts_config: {language, stem, remove_stop_words, with_position, ascii_folding, max_token_length}, harvest: <the harvest manifest>}` and passes `DF_SCHEMA.with_metadata({'ka.manifest': json})` to create_table. After the indexes: `table.tags.create(f"harvest-{harvested_at[:10]}", table.version)`. Also write `<db>/df.manifest.json` so the identity is readable with `cat` on a mounted volume. 3. lib: `dataset.py: read_manifest(table) -> Manifest | None` (pydantic) from `table.schema.metadata[b'ka.manifest']`; DfSearch gets `.manifest` cached at construction. 4. mcp: readiness() returns `(True, manifest_summary)` → `/ready` body `{"status":"ready","table":"df","snapshot":{"harvested_at":..., "records":6876, "coverage_pct":100.0, "content_digest":"sha256:…"}}`. format_results() gains a `footer` argument; df_tool passes `Snapshot: df harvested 2026-07-14, 6,876 of 6,876 live records (100%), digest ebdf715b` — one line, after the pagination line. format_charter gets the same line. Register `@mcp.resource("kansallisarkisto://df/snapshot")` returning the full manifest as JSON: MCP resources are the protocol's own primitive for 'static context', so a client can pull identity without spending a tool call. server.py:log_table_status() logs the same line at boot. 5. Missing manifest (a table built by an older ingest) is not an error: footer says `Snapshot: df (no manifest — built before v0.2)`.

**Why it is once-in-a-lifetime.** No archival MCP server today can be cited with a dataset identity; this one would answer 'what exactly are you searching' in the same breath as the result, from stdio on a laptop to /ready in Kubernetes, with one JSON object whose hash chain runs harvest→ingest→response. It is what makes the ra-mcp/ape-mcp siblings' next corpus a week's work: the manifest is corpus-agnostic.

**How we would know.** `/ready` and the `kansallisarkisto://df/snapshot` resource return a `content_digest` equal to the one `harvest.py` wrote; `test_routes.py` asserts the snapshot block; a new test ingests the fixture with a synthetic manifest and asserts the footer text of df_search and df_get_charter contains its date and digest; `make test-mcp` (scripts/mcp_smoke.py) gains a 7th check reading the resource. Zero tool-output growth beyond one line (≤ 120 chars) per reply.

**Risks.** Adds ~100 chars to every tool reply — the project treats tool text as load-bearing for the model; keep it one line, last, and stable so the model learns to ignore it. Schema metadata is bytes-keyed and ≤ manifest size; a 19 GB tuomiokirjat manifest with 22 shortfall cells is still < 10 KB. FastMCP 3.x resource registration must not be tried on stdio clients that lack resource support — harmless, they just don't list it.

**First step.** PR: `harvest.py` writes `harvested_at`, `base_url`, `file_sha256`, `record_count`, `harvester.git_sha` into report.json (10 lines, 1 test on a tmp dir); `ingest_df` reads the sibling report.json if present and passes it through `DF_SCHEMA.with_metadata`; `test_ingest.py` asserts `df_table.schema.metadata[b'ka.manifest']` round-trips.

**Spike.** Already run: scratchpad/spike/determinism.py — ingest the 18-row fixture with `DF_SCHEMA.with_metadata({...})`, then build_fts_index + build_scalar_indexes, then `db.open_table('df').schema.metadata` → metadata intact; `table.tags.create(...)` → `{'harvest-2026-07': {'version': 4, ...}}`. ## `repro-2` — An order-independent corpus digest and `harvest.py --diff`: make a re-harvest a first-class event with a changelog of records added, removed and changed

**survived 3/3, with corrections · effort S · impact 4/5**

**What the code does today.** scripts/harvest.py:311 writes each hit as `json.dumps(hit, ensure_ascii=False)` in the order the service returned it, no sort_keys — so two harvests of an unchanged index can differ byte-for-byte, and `sha256sum df.jsonl.gz` proves nothing. harvest.py:346-373 `verify()` checks only uniqueness of objectID and JSON well-formedness. harvest.py:291 `jsonl.unlink()` — a non-resume run deletes the previous snapshot before fetching, so there is nothing to compare against. data-sources.md:68-69 records the only drift ever observed ('voudintilit went from 99,031 to 99,125') as an anecdote: which 94 documents, and whether any of the other 99,031 changed text, is unknown and unknowable now. README.md:190 repeats it.

**The gap.** The project knows the index moves and cannot say how. 'Re-harvesting df reproduces the stored snapshot record for record' (data-sources.md:21) is a claim with no mechanism behind it. Kansallisarkisto re-recognising 500 pages of HTR would be invisible.

**The proposal.** In `harvest.py`: - `record_hash(rec) = sha256(json.dumps(rec, sort_keys=True, ensure_ascii=False, separators=(',',':')))`; `content_digest = sha256(concat of sorted 'objectID\0hash\n'))` — order-independent, so service ordering and gzip member boundaries stop mattering. Computed streaming during the write (one extra sha256 per record), written to the manifest (repro-1) together with a sidecar `<index>.hashes.tsv.gz` (objectID\thash; ~60 B/record → ~450 MB for tuomiokirjat, 400 KB for df). - `--diff <previous-dir>`: compares hashes.tsv of the previous snapshot with the new one and writes `changelog.json`: `{added:[objectID…], removed:[…], changed:[{objectID, df, fields:[…]}], counts, previous_digest, new_digest}`. Field-level diff only for `changed` (re-read those lines from both files — for df it is trivial; for tuomiokirjat it is a second streaming pass over both files keyed on the changed set). - `--keep-previous`: rename the old `<index>/` to `<index>.prev-<harvested_at>/` instead of unlink at harvest.py:291. - `Makefile: harvest` gets `--diff .data/df.prev --keep-previous`; docs/how-it-works/data-sources.md gets a 'What changed since the last harvest' table generated from changelog.json. - Tests: run `test_retrieval_quality.py`'s reachability sweep (line 111) on both snapshots when `.data/df.prev` exists, so a re-harvest that makes a record unfindable fails before ingest.

**Why it is once-in-a-lifetime.** This turns 'the live service is always the authority' from a disclaimer into an audit trail: each re-harvest documents exactly what the archive changed, at record and field level, in a minute of CPU for the 7.8M-page corpus. Digital-humanities projects almost never have this, and it is what allows a historian to reconcile results across two snapshots.

**How we would know.** Harvesting the fixture twice in reversed line order yields the same content_digest (spike: True). A synthetic diff of the fixture (1 added, 1 removed, 1 transcript edit) produces `{added:1, removed:1, changed:1, fields:['transcript']}` (spike: exact). Digest throughput ≥ 100k records/s single core, so tuomiokirjat adds ≤ 2 min to a 90-min harvest (spike: 115,818 rec/s on 2.4 KB records → 1.1 min). `make verify-data` prints the digest and it matches the manifest.

**Risks.** The hash sidecar for tuomiokirjat is ~450 MB — acceptable beside a 6.3 GB harvest, but should be gzip'd and git-ignored like the rest. Field-level diff on a 19 GB file is a second pass; bounded by streaming. Does not resolve *why* a record changed — only that it did.

**First step.** PR to scripts/harvest.py: compute record hashes during the write loop, add `content_digest` and `record_count` to report.json, add `--diff PREV_DIR` producing changelog.json, with tests on two tmp-dir snapshots built from the fixture. ~120 lines including tests.

**Spike.** Already run: scratchpad/spike/digest.py — order-independence True, synthetic diff exact, 115,818 rec/s hashing. Re-run: `/tmp/uvenv/bin/uv run python scratchpad/spike/digest.py <outdir>`.
