## `oss-1` — The server advertises fastmcp's version as its own: wire serverInfo.version to the package version

**pending (0/3 verdicts in) · effort S · impact 4/5**

**What the code does today.** packages/kansallisarkisto-mcp/src/ra_mcp_kansallisarkisto_mcp/tools.py:17-19 constructs `FastMCP(name="ra-kansallisarkisto-mcp", instructions=...)` with no `version=`. fastmcp 3.4.4's server.py:326 accepts `version`, and server.py:417 falls back to `fastmcp.__version__` when it is None. Measured with an in-memory client (scratchpad/spike_contract.py): `initialize` returns `serverInfo: ra-kansallisarkisto-mcp 3.4.4 protocol 2025-11-25` — a client logs 3.4.4 for a server whose pyproject says 0.1.0 (packages/kansallisarkisto-mcp/pyproject.toml:3). Meanwhile telemetry.py:56-66 already resolves the real version via `importlib.metadata.version("ra-mcp-kansallisarkisto-mcp")` for the OTel `service.version` resource attribute, so the project has two notions of its version and the one on the wire is wrong. publish.yml:44-56 validates the tag against both pyprojects, so the tag is already the source of truth for the third notion.

**The gap.** When v0.1.0 is released, every MCP client, registry listing and bug report will identify the server as 3.4.4; a dependabot bump of fastmcp will silently 'release' a new server version to every client while the tool contract has not changed. A reference MCP server must report its own version in `initialize`.

**The proposal.** Add `__version__` to `ra_mcp_kansallisarkisto_mcp/__init__.py` (currently a one-line docstring) via `importlib.metadata.version("ra-mcp-kansallisarkisto-mcp")` with the same `PackageNotFoundError -> "0.0.0+unknown"` fallback telemetry.py uses; pass `version=__version__` at tools.py:17; make telemetry.py:66 import it instead of re-resolving. Add `test_server_reports_its_own_version` to packages/kansallisarkisto-mcp/tests/test_tools.py: `client.initialize_result.serverInfo.version == importlib.metadata.version(...)` and `!= fastmcp.__version__`. Add the same assertion to scripts/mcp_smoke.py (a 7th check) so the published image is verified to report the tag it was built from — publish.yml already runs `test-published`.

**Why it is once-in-a-lifetime.** It is the difference between a server that can be cited ('kansallisarkisto-mcp 0.3.1 returned DF 2457') and one that cannot. Every other proposal in this list — contract versioning, data versioning, registry entries — hangs a version on the wire, and today that hook is the framework's number.

**How we would know.** `initialize` returns `serverInfo.version == "0.1.0"` on the v0.1.0 image (mcp_smoke.py check 7 green in publish.yml); a fastmcp bump PR leaves serverInfo.version unchanged; the OTel `service.version` and the MCP `serverInfo.version` are the same string in test_telemetry.py.

**Risks.** `fastmcp inspect --format mcp` (used by proposal oss-7's manifest) reads serverInfo too, so it must be regenerated. None otherwise; the change is ~10 lines.

**First step.** One PR: `__version__` in `__init__.py`, `version=__version__` at tools.py:17, telemetry.py:66 imports it, one test in test_tools.py, one check in mcp_smoke.py.

**Spike.** Run `uv run python scratchpad/spike_contract.py` (in-memory fastmcp Client against tools.kansallisarkisto_mcp): prints `serverInfo: ra-kansallisarkisto-mcp 3.4.4 protocol: 2025-11-25`. After the fix the same script must print 0.1.0.

## `oss-2` — Snapshot the wire-level tool contract and make 'breaking' a tested, documented property of an MCP release

**pending (0/3 verdicts in) · effort M · impact 5/5**

**What the code does today.** The tool contract exists only as Python annotations in df_tool.py:87-170 (df_search: 10 params with `ge`/`le` bounds, defaults `limit=25`, `fuzzy=0`, `match_all=True`) and df_tool.py:213-215 (`df_number` ge=1). test_tools.py:26-28 asserts only the set of tool names; scripts/mcp_smoke.py:36 likewise. cliff.toml:15 marks `(**BREAKING**)` only from `commit.breaking`, i.e. a `!` or BREAKING footer — and `git log` over all 51 commits contains zero such markers, although `a99bbf0 fix(lib): stop discarding fuzzy on a phrase` turned a silently-ignored parameter into an error reply and `f84c229 docs(mcp): sharpen the tool descriptions` rewrote what the model is told. formatter.py:67 and dataset.py:469 fix the output shapes `**DF N** — dating — place` and `... search results for '...': showing X of Y records (offset N)` that a downstream agent or eval parses. Measured (scratchpad/spike_contract.py): the full `tools/list` dump is 7,956 bytes; the structural subset (names, param names, types, bounds, defaults, required) is 868 bytes; descriptions alone are 1,638 + 567 chars.

**The gap.** For an MCP server the tool schema and the text format are the API. A rename of `issuingplace`, a change of `le=MAX_LIMIT` to 50, a flipped `match_all` default, or a new result header line breaks every client prompt and eval built on it, and nothing in CI or in the release notes would say so. 'Tool-contract changes are breaking changes' is not encoded anywhere.

**The proposal.** (1) Commit `packages/kansallisarkisto-mcp/contract/tools.json` — the sorted `tools/list` dump — and `contract/output.txt` — the fixture output of two canonical calls (`df_search(keyword="Åbo", limit=2)`, `df_get_charter(526)`). (2) `tests/test_contract.py`: compute the structural hash (drop `description` keys) and compare to the file; a mismatch fails with the diff and the instruction `make contract` — and `make contract` refuses unless `git log -1` carries `!` or `BREAKING CHANGE:`. Description-only drift is a separate, non-failing test that prints the diff (descriptions are tuned often — f84c229 — and must stay cheap). (3) `docs/tools/contract.md`: the policy — breaking = tool renamed/removed, parameter renamed/removed/retyped, a bound tightened, a default changed, the header/record/footer lines in format_results and _render_charter changed; non-breaking = new optional parameter with a default, description text, snippet length (SNIPPET_CHARS). Semver: breaking -> minor while 0.x, major after 1.0. (4) cliff.toml: add a first `commit_parsers` entry `{ message = "^(feat|fix|refactor)\\(tools\\)!", group = "<!-- 0 -->Tool contract (BREAKING)" }` so those commits lead the release note. (5) publish.yml: `fastmcp inspect ... --format mcp -o manifest.json` and attach `manifest.json` + `contract/tools.json` as release assets beside the SBOMs (lines 150-157), so a consumer can diff two releases' contracts without running either.

**Why it is once-in-a-lifetime.** No archival MCP server publishes a machine-diffable tool contract per release. Doing it here, with the output format included, turns 'a historian trusts and cites it' into something an eval can pin: the string that reaches the model at v0.2.0 is the string that was reviewed.

**How we would know.** A PR changing `le=MAX_LIMIT` at df_tool.py:106 to 50 without `!` fails CI at test_contract.py; the v0.2.0 release page carries `manifest.json` and `contract/tools.json` and a 'Tool contract (BREAKING)' section whenever the structural hash changed since the previous tag; `diff <(jq . v0.1.0/contract.json) <(jq . v0.2.0/contract.json)` is the documented way to read a release.

**Risks.** Two snapshot files to keep current; the description-drift test must stay informational or it will be resented and deleted. The `!` check in `make contract` is local policy, not a hard gate, until branch protection exists (audit finding 11: `main` has none).

**First step.** PR 1: generate `contract/tools.json` from the spike script, add `test_contract.py` with the structural-hash comparison and `make contract`; PR 2: `docs/tools/contract.md` and the cliff.toml parser.

**Spike.** `uv run python scratchpad/spike_contract.py` already produces both hashes (full 287c5a16…, structural 35941af6…) and prints the `fuzzy` and `limit` schema fragments `{default:0,min:0,max:2}` / `{default:25,min:1,max:100}` that the snapshot would pin. Change `le=MAX_LIMIT` to `le=50` in a scratch copy and rerun: the structural hash changes, the description-only hash does not.

## `oss-3` — Release the data too: a versioned, manifest-carrying LanceDB table published beside the image, with the server reporting code and data versions together

**pending (0/3 verdicts in) · effort L · impact 5/5**

**What the code does today.** README.md:112-114 and .gitignore: 'No corpus ships with this repository … the data is re-harvested rather than versioned'. deployment.md 'Release' versions only code. ingest.py:26-48 declares DF_SCHEMA; ingest_df builds the FTS index (dataset.py:136-192) and scalar indexes at ingest; server.py:24-50 logs table names at boot but no data identity; routes.py `/ready` reports only `df`. data-sources.md records that the live index moves (voudintilit 99,031 -> 99,125 between harvests) and that df harvest is 100% (README:32) — 3 MB, ~3 s. Measured on the fixture (scratchpad/spike_manifest.py): ingest is 0.04 s; `table.replace_field_metadata("object_id", {"data_manifest": json})` round-trips through `db.open_table().schema.field().metadata` (table-level `schema.metadata` is None, so field metadata is the available slot); two independent ingests of the same file give the identical ranked order for `Åbo` (7 hits) — the build is deterministic; the FTS config is readable back from `list_indices()[..].index_details`. README:40 gives the df table as ~69 MB.

**The gap.** A user who runs `docker run riksarkivet/kansallisarkisto-mcp:v0.1.0` has a signed, attested, SBOM'd image and nothing to search. 'Scales without changing shape' and 'the release is verifiable end to end' both stop at the data boundary: there is no way to say which harvest a result came from, no way to know a mounted table matches the schema the code expects, and a 69 MB artefact that takes 3 s to build is not shipped because of a philosophy written for the 19 GB corpus.

**The proposal.** (1) `ingest.py`: `DF_SCHEMA_VERSION = 1`; `ingest_df` writes a manifest — `{schema_version, table, source_path, source_sha256, source_rows, kept, skipped, harvested_at (from .data/df/report.json), fts: {language, stem, remove_stop_words, with_position, ascii_folding, max_token_length}, lib_version, lancedb, pyarrow, fingerprint}` — into field metadata on `object_id` AND as a sidecar `data/df.manifest.json` (readable by an operator with `cat`). `fingerprint` = sha256 of the ranked DF-number lists for 10 fixed queries (`konung`, `Åbo`, `ecclesia`, `"de ecclesia"`, `bref` fuzzy=1, …) so two ingests can be compared without comparing files. (2) `dataset.py`: `read_manifest(db, table)`; `tools.get_search()` refuses with a caller-fixable message when `schema_version != DF_SCHEMA_VERSION` ('table built for schema 1, this server needs 2 — run make ingest-df'); server.py:49 logs `data: df-2026.07.01 schema 1 rows 6876`; `/ready` JSON gains `data_version`; an MCP resource `kansallisarkisto://df/manifest` (a resource, not a tool, so oss-2's contract is untouched). (3) `.github/workflows/publish-data.yml` (Dagger `PublishData`): harvest df (3 s), ingest, verify fingerprint against the previous release, `tar` `data/df.lance` + manifest, push with `oras push docker.io/riksarkivet/kansallisarkisto-data:df-2026.09.09` with the manifest as OCI annotations, cosign-sign it keylessly exactly as the image is (publish.yml:160-166), attach the tarball as a release asset, and add a `data:` line to the release note template. (4) `docker-compose.yml` and deployment.md: a one-line `oras pull` (or `curl` of the release asset) before `up`. (5) Data version scheme `df-YYYY.MM.DD` (harvest date) with `+schemaN`; compatibility rule in `docs/how-it-works/data-sources.md`: a code release states the schema versions it accepts.

**Why it is once-in-a-lifetime.** An archive server whose every answer can be traced to (code version, data version, source hash, index config) is what lets a historian cite a result and a second researcher reproduce it a year later. The determinism is already there — it was measured today — it is just not captured.

**How we would know.** `docker run` + `oras pull` from the v0.1.0 release page yields `/ready` -> 200 with `data_version: df-2026.09.09`; two people ingesting the same harvest report the same fingerprint; a table built with schema 1 mounted under code expecting schema 2 answers `/ready` 503 with the re-ingest sentence rather than a lance error; the release note lists the data version and the 10-query fingerprint.

**Risks.** This argues against the stated philosophy ('re-harvested, not versioned') — and against README:195-201, which says the records are Kansallisarkisto's and reuse terms must be consulted. Publishing the table publicly needs written consent from Kansallisarkisto (see oss-6); until then ship only the manifest + fingerprint and keep the tarball as an artefact of a private workflow run. For tuomiokirjat the tarball path does not apply (19 GB); the manifest and schema-version handshake do, which is the part that 'scales without changing shape'. Field metadata on `object_id` is a slot, not a design; if lancedb adds table-level metadata, move it.

**First step.** PR: `DF_SCHEMA_VERSION`, manifest written by `ingest_df` (field metadata + sidecar), `read_manifest`, boot log line, `/ready` field, and the fingerprint over the 18-row fixture pinned in test_ingest.py. No publishing yet.

**Spike.** `uv run python scratchpad/spike_manifest.py` — already run: manifest round-trips via field metadata, FTS config reads back, two ingests give identical ranked order, 0.04 s / 0.2 MB for 18 rows. Extend it to compute the 10-query fingerprint and assert it is stable across 5 ingests.

## `oss-4` — Design the first release as a verifiable event: in-tree CHANGELOG on the site, OCI labels, a post-publish verifier, and badges that link to proof

**pending (0/3 verdicts in) · effort M · impact 4/5**

**What the code does today.** `git tag` is empty; 51 commits, every subject conventional (checked against cliff.toml's parsers — none would be dropped by `filter_unconventional = true`), so git-cliff can produce a complete v0.1.0 note. publish.yml:132-140 runs `git cliff --latest` only inside CI and only into the GitHub release body; cliff.toml:1-9 promises Keep-a-Changelog but no CHANGELOG.md exists and zensical.toml's nav has no changelog page. README.md:210-214 admits the three supply-chain badges 'state how this project releases, not yet something you can download and verify'; the SLSA/Sigstore/SBOM badges are static shields.io images linking to docs sections. publish.yml:97-109 (`docker/build-push-action`) sets no `labels:` and the Dockerfile has no `LABEL` (grep: none), so the pushed image carries no `org.opencontainers.image.version/revision/source`. `test-published` (publish.yml:170-177) only checks `/health` per deployment.md. zensical.toml:99 links a Docker Hub repo that does not exist yet; .docker/docker-compose.yml:2 pulls `riksarkivet/kansallisarkisto-mcp:latest`. Audit 2 finding 4 (dispatch can overwrite a version tag) and 'publish.yml runs test and scan-ci but not checks' are still open.

**The gap.** The pipeline is more elaborate than most released projects', and nothing has ever exercised it end to end — the first tag push is the first run of the provenance, release-asset and signing steps against a real registry. There is no cadence, no statement of what a release note must contain for an MCP server, and the badges are promises.

**The proposal.** (1) `make release VERSION=0.1.0`: sed both pyprojects, `uv lock`, `git cliff --tag v0.1.0 -o docs/changelog.md`, commit `chore(release): v0.1.0`, `git tag -s`. Add `docs/changelog.md` to zensical.toml nav ('Changelog'); docs.yml already rebuilds on push to main. (2) publish.yml: add `uv lock --check` and `dagger call checks` before `test` (closes the pip-audit gap); `docker/metadata-action` to emit OCI labels (`version`, `revision`, `source`, `licenses=Apache-2.0`, `title`); dispatch runs push `sha-<short>` only (closes audit finding 4). (3) A `verify-release` Dagger function run as the final step: `cosign verify --certificate-identity-regexp '^https://github.com/AI-Riksarkivet/kansallisarkisto-mcp/.github/workflows/publish.yml@refs/tags/v' --certificate-oidc-issuer https://token.actions.githubusercontent.com riksarkivet/kansallisarkisto-mcp@<digest>` and `slsa-verifier verify-image … --source-uri github.com/AI-Riksarkivet/kansallisarkisto-mcp --source-tag v0.1.0`, plus `test-published` extended to call `tools/list` over `/mcp` and check `serverInfo.version` (oss-1). (4) cliff.toml `footer`: a 'Verify this release' block with those two commands and `## Data` / `## Tool contract` / `## Retrieval behaviour` headings — the last for index/analyser changes that move counts (data-sources.md records konung 277 -> 279 after the apparatus fix; that is release-note material for a search server). (5) Badges: replace the three static shields with links to the verify-release job of the latest run (`actions/workflows/publish.yml/badge.svg` + `?event=push` on tags) and a 'Latest release' shield (`img.shields.io/github/v/release/...`) that is red-or-absent until a release exists; keep the earned ones (Tests, Security, CodeQL, Scorecard). (6) Cadence policy in `docs/development/deployment.md`: release immediately on any tool-contract change (minor while 0.x); a patch on the first Monday after Dependabot bumps land (Trivy and Dependabot both run Mondays — security.yml:18, dependabot.yml:7); a data release per harvest (oss-3).

**Why it is once-in-a-lifetime.** A release page from which a stranger can, with two copy-pasted commands, prove the image was built from this tag by GitHub's builder — and read in the same note which tool parameters and which search counts changed — is the standard the badges already claim. The first release is the only chance to set that shape before consumers exist.

**How we would know.** From a clean machine, the two commands in the v0.1.0 release body succeed; `docker inspect` shows `org.opencontainers.image.version=0.1.0` and `.revision=<sha>`; the site's Changelog page equals `git cliff`; OpenSSF Scorecard's Signed-Releases check moves from N/A to scored; every README badge resolves to a URL whose content is the evidence for the badge.

**Risks.** Signed tags require a maintainer GPG/SSH signing key — a small ceremony for a single-maintainer project (git shortlog: one author). `docker/metadata-action` is one more SHA-pinned action. The first real run of slsa-github-generator and cosign against Docker Hub may need secrets adjustments; do a `v0.1.0-rc.1` prerelease first and let `verify-release` fail there rather than on 0.1.0.

**First step.** PR: `make release`, `docs/changelog.md` generated from the current history (it is complete), nav entry, OCI labels, `uv lock --check` + `checks` in publish.yml, `sha-` tag for dispatch. Then cut `v0.1.0-rc.1`.

**Spike.** `git log --format=%s | grep -vE '^(feat|fix|docs|refactor|test|chore|ci|build|perf|style|revert)(\([^)]*\))?!?: '` returns nothing — the whole history is changelog-ready. (`uvx git-cliff` itself timed out downloading through the proxy here, so the rendered note was not previewed.)

## `oss-5` — Community files shaped by this corpus: an 'unfindable document' issue template that feeds test_retrieval_quality.py, a CONTRIBUTING that encodes 'measure it and write it beside the code', and a CITATION.cff that cites the archive

**pending (0/3 verdicts in) · effort S · impact 3/5**

**What the code does today.** None of CONTRIBUTING.md, CODE_OF_CONDUCT.md, CITATION.cff, CODEOWNERS, .github/ISSUE_TEMPLATE, PULL_REQUEST_TEMPLATE.md exist (checked). README.md:203-205 instructs 'Cite the archive, not this snapshot'. data-sources.md 'Can everything be found?' and test_retrieval_quality.py:1-20 describe the sweep that found three classes of silently-unfindable documents, each now pinned against the 18-row fixture; conftest.py:11-15 documents why each fixture charter is there. dataset.py:44-60 and models.py:14-22 show the house rule: every default carries its measured count. The audits call the retrieval-quality suite 'the most valuable thing in the repository'. Audit 2 finding 9 shows the numbers drift (27 vs 28 compound-language charters).

**The gap.** The project's best mechanism — a researcher notices a charter they cannot find, and it becomes a pinned test — has no intake. A historian who searches `Hundæbæth` and gets nothing has nowhere to report it that would turn it into a fixture row; a contributor has no statement of the rules the code visibly follows; a researcher citing the software has no metadata to cite.

**The proposal.** (1) `.github/ISSUE_TEMPLATE/unfindable.yml` (form): DF number; the word searched; the form in the transcript at df.kansallisarkisto.fi/document/N (required checkbox 'I checked the archive page'); filters used; `fuzzy` tried (0/1/2); expected vs got. Label `retrieval`. (2) `.github/ISSUE_TEMPLATE/tool-contract.yml` for a parameter/description problem — the audit's `fuzzy`-on-phrase class. (3) `CONTRIBUTING.md`, short, with the three rules the code already obeys and the audits enforce: a default that changes a count carries the count in a comment and, where the fixture can show it, a test; a change to df_tool.py's schema or formatter's line shapes follows `docs/tools/contract.md` (oss-2) and a `!` commit; a fixture addition to df_sample.jsonl states which trap the charter covers (conftest.py style) and updates the fixture count everywhere via `wc -l` (audit 1 finding 6). Plus: `make check`, `make test`, `make test-mcp` before a PR; corpus-only tests are skipped without `.data/df` and how to harvest it in 3 s. (4) `CITATION.cff`: `type: software`, authors = Riksarkivet AI lab and (per oss-6) Kansallisarkisto, `repository-code`, `license: Apache-2.0`, and a `references:` entry for Diplomatarium Fennicum with `url: https://df.kansallisarkisto.fi` so the archive citation the README demands is machine-readable; GitHub then shows 'Cite this repository'. (5) `CODE_OF_CONDUCT.md` = Contributor Covenant 2.1 with the SECURITY.md contact. (6) `.github/PULL_REQUEST_TEMPLATE.md` with two checkboxes: 'tool contract unchanged, or commit carries `!`' and 'every new number in a comment or description was measured on the corpus (say which harvest)'.

**Why it is once-in-a-lifetime.** The issue template is a retrieval-quality pipeline with humans as the sweep. Done right, the fixture grows from 18 to the charters real researchers could not find, and the test suite becomes the documented history of the corpus's traps.

**How we would know.** GitHub community-profile checklist at 100%; Scorecard 'Contributing' signals present; the first `retrieval`-labelled issue lands as a fixture row + parametrised case in test_retrieval_quality.py within one release, with the fixture count updated in the seven places audit 1 listed.

**Risks.** Templates nobody triages become noise; the single-maintainer situation (oss-6) is the real constraint. Adding charters to the fixture slows the suite negligibly (ingest 0.04 s for 18 rows).

**First step.** One PR adding the six files; CITATION.cff validated with `cffconvert --validate` in CI's `checks` (a `uvx cffconvert` line in .dagger/checks.go).

## `oss-6` — Make Kansallisarkisto a co-owner by structure: CODEOWNERS over the material-facing files, a vocabulary file only the archive can bless, a data-terms document, and a Finnish/Swedish front door

**pending (0/3 verdicts in) · effort XL · impact 5/5**

**What the code does today.** zensical.toml:5-8 `site_author = "Riksarkivet"`, `Copyright 2026 Riksarkivet`; package names carry Riksarkivet's prefix on Finland's data (`ra-mcp-kansallisarkisto-lib`, packages/kansallisarkisto-lib/pyproject.toml:2); the image namespace is `riksarkivet/` (publish.yml:15); SECURITY.md:14-18 positions Kansallisarkisto as a third party ('belong to Kansallisarkisto, not here'). `git shortlog -sne`: one human author. There is no Finnish- or Swedish-language page anywhere in docs/. The material knowledge lives as prose only Kansallisarkisto's cataloguers can authoritatively confirm: tools.py:36-44 (the 75-value index-term vocabulary with counts), df_tool.py:107-136 (15 language labels, 499 places, the Reval/Tallinn rule) — 29 + 61 hard-coded numbers in those two files (counted), and audit 2 found them already drifting (27 vs 28). data-sources.md 'Provenance': the 1.75% shortfall (141,032 documents) is retrievable only via the ES API at es.demo.kansallisarkisto.fi 'with an API key from Kansallisarkisto'. README:195-201 defers reuse terms to Kansallisarkisto without a document saying what they are.

**The gap.** Everything about ownership is Riksarkivet's and everything about authority over the content is Kansallisarkisto's, and the repository has no structure through which the second can act: no reviewable artefact for the vocabulary, no place to sign off on data terms, no path that needs a Finnish account to merge, no language the Finnish archive's own staff would land in.

**The proposal.** (1) `.github/CODEOWNERS`: `docs/how-it-works/data-sources.md`, `docs/how-it-works/search-tips.md`, `packages/kansallisarkisto-lib/src/ra_mcp_kansallisarkisto_lib/vocab/`, `packages/kansallisarkisto-lib/tests/fixtures/`, and `packages/kansallisarkisto-mcp/src/ra_mcp_kansallisarkisto_mcp/df_tool.py` owned by `@AI-Riksarkivet/ka-material` (a team with Kansallisarkisto accounts) in addition to the code team; enable branch protection with 'require review from code owners' — which also closes the Scorecard Branch-Protection and Code-Review zeros (audit 2 finding 11). (2) `scripts/vocab.py` regenerates `vocab/df.json` from the harvest: index terms, language labels, countries, top-50 places, each with its count and the harvest date; a test asserts every number quoted in df_tool.py and tools.py appears in vocab/df.json (or the descriptions are rendered from it with `{counts[...]}` placeholders) — the drift audit 2 found becomes a failing test, and a Kansallisarkisto reviewer sees vocabulary changes as a JSON diff, not as prose. (3) `DATA_TERMS.md` (linked from README 'Credit and licence' and SECURITY 'Scope') co-authored with Kansallisarkisto: what may be redistributed (the built table? the fixture's 18 real charters, which are already in the repo?), attribution string, and the API-key route for the 1.75% — this is the document that unblocks oss-3 and legitimises the fixture. (4) `GOVERNANCE.md`: two maintainers, one per archive, both required on contract (`!`) and data-terms changes; anything else one review. (5) `docs/index.fi.md` and `docs/index.sv.md` — a one-page landing in Finnish and Swedish (the material is Swedish; Finland is bilingual), linked from the site header; the tool `instructions` already tell the model to answer in the user's language (tools.py:57-59), the docs should meet the same bar. (6) Naming: register the neutral PyPI names `kansallisarkisto-mcp` / `kansallisarkisto-lib` (oss-7) and keep the `ra_mcp_` import path; move the image to a shared org namespace only when both archives agree — say so in GOVERNANCE.md rather than silently keeping `riksarkivet/`.

**Why it is once-in-a-lifetime.** A cross-border national-archives project where the code owner and the record owner both hold a key is rare enough to be cited as a model.
